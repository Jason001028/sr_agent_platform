## 1. 这套系统是做什么的

一句话定位：为遥感影像提供**浏览、区域圈定、超分计算**三类能力。

- **浏览**：在网页中打开单幅数百 MB～1.8GB 的 16bit 灰度卫星影像，数秒内查看全貌。
- **区域圈定**：在影像上以矩形 / 多边形 / 魔棒圈定待处理区域，生成该区域的全分辨率掩码。
- **超分计算**：对低分辨率影像执行超分模型（SR）放大重建。模型运行于**内网的 GPU 集群**（Slurm 调度作业）；网页仅负责提交作业、查询进度、获取结果，不承担计算。

使用者为遥感业务人员；后续演进方向是多人共享同一条 GPU 作业队列。

**四个页面（路由）对应四项能力**：

| 页面（路由） | 能力 | 状态 |
|---|---|---|
| `/viewer` 查看器 | 打开**本地文件**的 TIF，交互浏览 + 绘制掩码 + 导出 JPG | 阶段 3 完成 |
| `/scenes` 盘阵场景 | 检索**内网盘阵图库**并打开（读取服务端预生成的 JPG） | 阶段 4 完成 |
| `/chat` 聊天 | 以自然语言驱动 Agent 执行任务（Agent 自主调用工具） | 阶段 5 规划中 |
| `/queue` 任务队列 | 多人共享的 SR 作业队列（提交 / 取消 / 实时状态） | 阶段 5 规划中 |

**一条典型主流程**（完成全部阶段后的形态）：

```
遥感业务人员
 ├─ 在 /scenes 检索到某景图 → 打开 8192 概览（服务端预生成的 JPG）
 ├─ 在图上以矩形圈定河流区域 → 得到掩码（0/255 + 质心 txt）
 ├─ 在 /queue 提交 SR 作业（或由 /chat 中的 Agent 调用 run_sr 提交）
 └─ 队列页实时看到 PENDING → RUNNING → COMPLETED，获取超分结果
```

> 技术本质：这是一个常规的「前端 SPA + 后端 API」应用。难度集中在两点——**被浏览的数据体量特别大**（单幅数百 MB～1.8GB）与**运行环境受限**（内网、浏览器资源上限），即下一章的三项硬性约束。
>
> **本节向上汇报（可直接引用）**：平台定位为面向遥感影像的 Web 系统，提供浏览、区域圈定与超分计算三类能力；浏览与圈定在网页端完成，超分模型运行于内网 GPU 集群，网页仅承担作业提交与结果获取。

## 2. 三项硬性约束（后续设计的共同前提）

> 本章是仓库设计的依据：多数非常规设计与阶段划分均可用以下三项约束解释。后文介绍每项技术时都会回溯到对应约束。

### 约束 1：浏览器单次内存分配上限约 2GB，Canvas 画布面积上限约 16384²

**事实**：Edge/Chrome 中 `new Uint8Array(...)` 的单次分配超过约 2GB 即抛 `RangeError: Array buffer allocation failed`——与机器物理内存无关。Canvas 画布边长存在约 16384 的软上限。

**推论**：一幅 2.4 万 × 2.4 万像素的 16bit 灰度影像，像素数据约需 `W×H×2 ≈ 1.2GB`，转为 RGBA 后约 2.4GB，超出单次分配上限，浏览器无法整幅解码。因此系统采用"先出概览、按需读取"的策略：或仅抽样读取部分行（稀疏条带），或读取服务端预生成的降采样 JPG。

该约束直接决定了阶段 1 的**解码分派决策树**、阶段 4 的**服务端预生成 JPG**，以及"浏览器承担尽量少的处理、重处理放后端"的整体分工。

### 约束 2：部署环境为内网离线、CDN 不可达，第三方库须本地内置

**事实**：部署与使用环境为内网，无法访问 jsdelivr 等公共 CDN；任何对 CDN 的 `import` 都会导致页面无法加载。

**推论**：前端所有第三方库（TIFF 解码、压缩等）必须**本地内置**（源码或压缩文件置于 `frontend/src/vendor/`，随构建打进产物）。由于库一旦内置替换成本较高，阶段 1→3 遵循两条纪律：**先将核心算法抽为与框架无关的 TS 并建立像素级基线对照测试；UI 层做迁移而非重写**——更换 UI 框架不动算法，无法更换的库也不至于推翻既有实现。

### 约束 3：真实数据仅存于内网盘阵机，外网开发机无法访问

**事实**：开发机为**外网机**；真实的 1.1GB / 1.78GB 影像全部位于内网 CentOS7 盘阵机，**无法导出、无法探测文件头**。文件结构只能依据用户回传的 ENVI 头信息（压缩方式 / 波段布局）或影像尺寸推断。

**推论**：开发环境无法做真机联调，因此对一切"需对接真实外部系统"的功能均提供**可测试的替身**（本仓库贯穿始终的核心方法论）：

| 真实系统 | 开发机替身 | 触发条件 |
|---|---|---|
| 盘阵图库 | 确定性假数据（`fake:true` 标记） | 未设置 `SR_SCENES_ROOT` |
| LLM（Agent 的大模型） | 固定脚本假 chat（mock） | `SR_LLM_MOCK=1`（阶段 5） |
| Slurm GPU 调度器 | 内存假调度器 | `SR_SLURM_FAKE=1`（阶段 5） |
| 命令行执行器 | 注入假 `run_cmd` | 测试代码中注入 |

**约束原则**：测试替身必须**显式标记**（`fake:true`、路径含 `<fake>`），且真实消费端必须**拒绝假数据**——否则开发机上通过的假流程，在真机会把占位路径当作真实文件提交给 Slurm。

> 三项约束是后续所有设计的前提。以下从零逐步构建系统。
>
> **本节向上汇报**：方案的设计前提可归纳为三项约束——浏览器单次内存分配上限约 2GB、内网离线环境要求第三方库本地内置、真实数据无法在外网开发机访问。全部架构决策均围绕这三项前提展开，并据此确立了对真实外部系统一律采用"显式标记、可被拒绝"的测试替身进行开发验证。

## 3. 技术选型 + 仓库地图

### 3.1 为什么是这四样

| 层 | 选型 | 一句话理由 |
|---|---|---|
| 前端框架 | Vue3 + TypeScript（Vite 构建） | 多页面共享同一查看器画布与一套全局状态，适合响应式渲染与集中式状态管理 |
| 后端 | FastAPI（REST + SSE） | Agent / SR / 图像工具均以 Python 实现，REST 与服务端推送（SSE）可由同一框架覆盖 |
| 作业调度 | 沿用 Slurm | 4 张 GPU 已在用 Slurm 排队；平台仅作为 Slurm 的网页客户端 |
| 任务记录 | SQLite | 单机部署、无需独立服务；`sr_tasks` 表同时用作幂等表防止重复提交 |

两个明确的排除项，避免混淆：

- **不引入 Spring Boot 等大型全家桶**：公司无统一技术标准，遥感后端全部基于 Python，额外引入 Java 门面只增加维护成本。
- **不基于 LangChain/LangGraph 开发**：Agent 流程较短，以约 200 行自写状态机实现更可控；当出现"跨小时断点续跑 / 人工审核"等需求时，再评估引入 LangGraph 薄封装。

选型完整推演见 [docs/status/current-question.md](docs/status/current-question.md) §3.1 的决策表。

## 4. 阶段 1：将影像解析核心算法抽为与框架无关的 TS

### 4.1 为何先抽离算法、后接入 UI

最早的查看器是**单文件 HTML**（`tif_viewer/tif-viewer.html`，已冻结），算法与 DOM 写在一起。将其改造为 Vue 应用时确立纪律：**迁移而非重写**。

- 算法层（读 TIF、亮度拉伸、稀疏采样、掩码栅格化）此前已验证并修复了各类缺陷，改造时**逐字节保留**，仅调整存放位置。
- 将其抽为**与框架无关的 TS**：不依赖 Vue、不接触 DOM、不接触 canvas——从而可在 Node 中直接运行，进行**像素级基线对照测试**（输入已知影像，断言输出每个像素的值）。

仓库体现：`frontend/src/lib/tifDecode.ts`、`maskgen.ts`、`viewMath.ts`、`source.ts`。UI 层（页面 / 组件 / store）仅 import 这些纯函数，不重写其内部逻辑。

### 4.2 遥感与 TIFF 基础词汇

阅读算法前需掌握的最小词汇表（每个词一句话）：

| 词 | 是什么 | 为什么重要 |
|---|---|---|
| TIF / BigTIFF | 图像容器格式。BigTIFF 为大文件扩展（使用 8 字节偏移量） | 格式不同，偏移量解析代码不同 |
| 位深 bits | 每像素位数。卫星影像通常为 **16bit**（0~65535）灰度 | 值域大，直接显示会整体偏黑 → 需拉伸 |
| 条带 strip | TIFF 按"若干行一组"存放像素（strip per row = 每行一组） | 真实大图为**无压缩 + 每行一条带** → 可按字节精确定位任一行 |
| 无压缩 (1) | compression=1，像素数据以原始形式存储 | 可定位并按需读取任意区域，**无需建立金字塔** |
| 压缩 8 | Deflate 压缩（掩码产物使用） | 掩码较扁平，压缩后文件较小 |
| photometric | 颜色语义：0=WhiteIsZero（白=0，需反色）、1=BlackIsZero | 未反色会导致影像颜色反转 |
| 单波段 | 单通道灰度影像 | 决定使用哪条解码路径 |

> 真机两张代表影像：GF07A03（1.11GB）、KF02B04（1.78GB），均为**无压缩 + 每行一条带 + 单波段 16bit**。因布局规整，才可采取"稀疏抽样预览"而无需建立金字塔。

### 4.3 大影像解码分派（仓库核心判断逻辑）

浏览器读取一张 TIF 不能走单一解码路径，须先探测文件头、再按条件选择路径。伪代码：

```
探测文件头 → 获取 {W,H,位深,类型,压缩,photometric,是否BigTIFF}

if 小型 8bit 无符号整数且未超内存   → UTIF 整幅解码（最快）
else if 压缩/tiled/多波段 大影像     → geotiff 分块解码（逐块读取 + 进度条）
else if 无压缩 + 条带 + 单波段 + 大影像 → 稀疏条带预览（仅抽样读取若干行，秒级）
```

- **判断解码字节量**：`解码字节 ≈ W×H×通道数×(bits/8)`。超过安全线（仓库常量 `SAFE=1.3e9`）即须走分块/稀疏路径，否则触及约束 1 的 2GB 上限。
- **稀疏条带预览的效率**：真实影像每行一条带、无压缩，抽样第 k 行时可直接计算其在文件中的字节偏移并仅读取该段。预览目标长边 `SPARSE_PREVIEW_MAX=8192`（约原图长边的 1/3）。
- **BigTIFF 兼容性**：本地内置的 UTIF 库不支持 BigTIFF（解码后宽高返回 0），因此探测到 `big` 时强制走 geotiff 分块。这是迁移过程中唯一允许行为差异的情形——原单文件 HTML 在该条件下本身即为缺陷。

对应代码：决策函数位于 [frontend/src/lib/decode.ts](frontend/src/lib/decode.ts)（`needGeo` + `decodeOne`）；稀疏采样细节位于 [frontend/src/lib/tifDecode.ts](frontend/src/lib/tifDecode.ts)。

### 4.4 亮度拉伸：为何"原样显示"会整体偏黑

16bit 影像值域为 0~65535，而屏幕仅支持 0~255。直接映射会使绝大多数像素偏暗，因此显示前需**拉伸**：将"大多数像素所在的值区间"映射到 0~255。

- **min-max 线性拉伸**：以整幅影像最小/最大值作为映射端点。
- **2% Linear**：取 2% 与 98% 分位作为两端，**避免个别极亮/极暗像素主导整体映射**（卫星影像常见）。该档同时也是服务端预生成盘阵 JPG 的默认配置。
- 拉伸仅作用于**颜色通道**，alpha 通道永不缩放。此前曾出现全黑缺陷：alpha 被一并缩放（系数 ≈0.0039 × 255 ≈ 0）导致整幅透明，该约束已记录于 [gui-experience.md](docs/experience/gui-experience.md) §3。

> 阶段 1 的交付形态为"一组纯 TS 模块 + 一组基线单测"，此阶段无界面、无后端。其价值在于：后续 UI 无论如何调整，像素正确性的基准已由此固定。
>
> **本节向上汇报**：阶段 1 已完成核心影像算法的框架无关化抽离（解码分派、稀疏采样、亮度拉伸、掩码栅格化），并建立像素级基线对照测试作为后续改动的正确性基准；同时整理了阅读代码所需的 TIFF 基础术语。此阶段无界面与后端交付，属于基础层建设。

## 5. 阶段 2：Vue3 工程骨架

在纯算法之上，搭建一个可运行的 Vue3 网站，使算法可在其中被调用。

### 5.1 选型依据：Vue3 + Vite + Pinia + vue-router

- **Vue3 `<script setup lang="ts">`**：单文件组件，模板、逻辑、样式合为一个 `.vue` 文件。
- **Pinia**：承载跨页面 / 跨组件共享状态。查看器画布、当前影像、掩码多边形、队列任务等"多方读取、多方修改"的状态集中于 store。
- **vue-router**：管理 `/viewer` `/scenes` `/chat` `/queue` 四个页面。注意为 **history 模式**（URL 无 `#`），因此生产环境 nginx 需配置"未匹配路径回退到 `index.html`"（SPA 回退，见 §11）。
- **Vite**：开发期热更新，构建期打包为纯静态站点（交由 nginx 托管）。

### 5.2 浏览器环境 ≠ Node：为访问系统能力的代码提供依赖注入

纯函数（`lib/`）不接触 DOM/canvas，可直接单测；但"创建 canvas、写文件、读本地文件"等浏览器能力若在模块内直接使用全局对象，会使 Node 测试无法运行。处理方法是将系统能力封装为**依赖注入**：

- `lib/browserKit.ts`：封装创建 canvas 的"工具箱"，测试时注入假实现，运行时注入 `document.createElement`。
- `lib/saver.ts`：封装保存文件的三级降级方案（File System Access → IndexedDB → 传统下载）。
- `lib/source.ts`：抽象"给定偏移量，读取一段字节"的接口——本地文件一种实现；HTTP 曾为另一种实现，阶段 4 时 HttpSource 被废弃（见 §7），但该抽象保留。

> 通用原则：**需要测试的模块尽量保持纯函数；无法规避的系统能力尽量以参数/接口注入，避免在模块内直接引用全局对象**。

### 5.3 本地 vendor：无 CDN 环境下引入第三方库

无 CDN 时第三方库须内置到项目内。步骤：

1. 库文件（压缩版或源码）放入 `frontend/src/vendor/`（如 `utif.js`、`geotiff.min.js`、`pako.min.js`）。
2. 在 [main.ts](frontend/src/main.ts) 中以 import 完成接线，顺序有依赖关系：`pako → utif → geotiff`（geotiff 解 Deflate 依赖 pako）。
3. 构建时上述文件随产物打包 → **产物自带全部依赖，可离线使用**。离线打包脚本 [frontend/scripts/package-offline.sh](frontend/scripts/package-offline.sh) 将前后端产物打成可直接拷入内网的离线包。

> 版本红线：项目内打过补丁的 `utif.js` **不得重新安装**——重装会丢失补丁并复现已知缺陷（见 [CLAUDE.md](CLAUDE.md) 与记忆索引）。

### 5.4 git 边界

大测试图（`test-tifs/`）与浏览器端到端测试（`.e2e/`）均为**本机资产、不入 git**（体积大且涉及本机浏览器路径）。仓库仅保留小尺寸 fixture（`frontend/fixtures/`）。新成员 clone 后不携带数百 MB 测试图——不影响使用，测试脚本本身不依赖它们。

> **本节向上汇报**：阶段 2 完成 Vue3 工程骨架，确立路由 / 状态管理 / 本地 vendor / 离线构建四部分；第三方库全部本地内置，构建产物可离线部署。对浏览器特有能力统一以依赖注入封装，保证算法与状态逻辑可脱离浏览器独立测试。

## 6. 阶段 3：将查看器交互层整体迁入 Vue

阶段 2 已具备应用外壳与纯算法，阶段 3 将原 HTML 查看器的**交互层**（工具栏、画布事件、状态切换）迁入 Vue。

### 6.1 职责划分（六个组件 + 一个 store）

| 组件/模块 | 职责 |
|---|---|
| `components/TifCanvas.vue` | 双画布（影像画布 + 掩码叠加画布）+ 平移/缩放事件 + 绘制模式事件 |
| `components/Toolbar.vue` | 选文件 / 拉伸下拉 / 输出目录 / 定位 X·Y / 绘制掩码 / 生成掩码 |
| `components/FileList.vue` | 已打开文件列表 + 每文件的布局探测 / JPG 状态 / 移除 |
| `components/DrawPanel.vue` | 掩码工具（矩形 / 多边形 / 魔棒 / 删除 / 容差）+ 合并重叠 + 撤销清空 + 导出 |
| `components/DecodeOverlay.vue` | 解码遮罩 + 进度条 |
| `components/StatusBar.vue` | 状态栏（当前图 W/H、拉伸、坐标等） |
| `stores/viewer.ts` | **总调度**：文件列表、当前激活图、视图变换、解码、拉伸、掩码、导出等 |

核心设计：**组件之间不互相调用逻辑，仅向 store 发起请求；画布重绘统一由 store 的 `renderTick` 计数器触发**。任何组件修改状态后，重绘仅有一个入口，避免多处修改导致渲染状态不一致。

> 状态归属原则：凡是**跨组件共享、可能被并发修改**的状态放 store；仅在组件内部、与他人无关的临时 UI 状态可留在组件内。

### 6.2 打开影像后的流程（rec 模型）

打开本地文件 = 探测头部 → 按 §4.3 决策树解码 → 产出一条 **rec**（影像记录）：含 `W/H`、缩略图画布 `thumb`、像素数组 `src`、统计 `stats`、所用路径 `route`、状态文案等。当前屏幕显示的是"当前激活的 rec"，掩码绘制于其上。其结构可参考 [stores/viewer.ts](frontend/src/stores/viewer.ts) 中的 `openSceneJpg` / `decodeRec`。

### 6.3 Web 异步 UI 的通用原则（本仓库已落地的处理）

- **以"当前图"守卫异步回调**：解码为异步操作，期间用户可能切换影像 → 仅当"回调中影像仍是当前激活图"时才刷新 UI，否则丢弃回调，避免旧影像进度污染新影像界面。
- **以令牌防止重复副作用**：导出 JPG 为较重操作，用 `_jpgToken` 标记当前导出；用户中途再次导出或切换影像时，旧令牌作废。另一处：canvas `toBlob` 在内存不足时抛错，此时自动将导出尺寸从 8192 **降档至 4096 重试一次**。
- **异步删除的误删防护**：删除掩码区域前先闪烁提示 200ms 再执行删除，回调中校验"仍为同一影像"后才执行——防止提示期间切换影像造成误删。
- **大计算量操作分批让出主线程**：掩码合并等涉及数千万像素的操作若一次执行会阻塞页面，改为分批执行、每批 `yield` 一次并提供进度条；合并期间的其他操作结果将被丢弃。

> 上述均为**通用 Web 异步 UI**的处理模式，与遥感领域无关，值得记录。

### 6.4 掩码的绘制与存储（前后端统一约定）

预览图上绘制的多边形，其坐标最终换算回**全分辨率**（缩略图坐标 → 原图像素坐标，`thumbToOrig`）。产物格式前后端统一：

- `掩码.tif`：uint8 灰度，像素仅取 **0/255**（0=不处理、255=要处理），Deflate 压缩；尺寸与原影像一致。
- `掩膜中心点坐标.txt`：参考文件的固定格式（UTF-8、CRLF、两行全角表头），每区域一行 `序号,质心X,质心Y`（面积质心，2 位小数）。

填充约定须**前后端一致**：顶点为像素中心、边界像素**含在区域内**。因此"多边形栅格化"在前端 [maskgen.ts](frontend/src/lib/maskgen.ts) 与后端 [services/mask.py](backend/services/mask.py) **各实现一份，再以逐像素对比测试相互校验**——前端可能直接导出掩码下载，后端也需要独立产出。

> **本节向上汇报**：阶段 3 已将查看器交互层整体迁入 Vue，组件统一向 store 发起请求并以 store 为状态唯一入口，掩码产物格式与后端约定一致；解码、导出、删除、合并等异步操作均完成竞态防护。查看器交互能力与阶段 1~2 保持等价。

## 7. 阶段 4：后端 FastAPI 首次介入 —— 盘阵场景读取服务端 JPG

阶段 1~3 均为"本地文件路径"：浏览器自行读取本地 TIF。阶段 4 将**内网盘阵**接入，同时**后端首次提供 HTTP API**。

### 7.1 盘阵场景为何改为"读取服务端预生成的 JPG"

盘阵真实影像为 1.1~1.8GB。若由浏览器直接读取，将触及约束 1（2GB / 16384²），且需在浏览器侧实现"按 Range 读取 TIF 字节"的复杂逻辑（原计划的 HttpSource 已被废弃）。因此改为更清晰的职责分工：

1. **显示侧**：读取服务端预生成的 8192 长边 JPG（稀疏采样与 2% 线性拉伸已写入像素），浏览器仅以 `<img>` 或 canvas 呈现。
2. 浏览器**不再接触盘阵原始 TIF 字节**，从机制上消除 2GB 与 16384² 两项约束在盘阵场景下的影响。
3. **本地文件路径保持原读取方式**（仍走稀疏 TIF 读取），阶段 1~3 的行为不做改动；两种数据源并存。

后端随之首次承担图像处理职责：在盘阵机本地读取 TIF、生成 JPG、托管静态产物——"重处理放数据所在机器"的原则在盘阵场景落地。对应决策见 [docs/status/current-question.md](docs/status/current-question.md) §3.4 与 §9，及 gui-experience §9。

### 7.2 FastAPI 最小骨架

后端 [backend/api/app.py](backend/api/app.py) 为函数工厂 `create_app()`，所有路由挂在 `/api` 下，配置全部来自环境变量（见 §11）。两个核心端点：

- `GET /api/scenes`：盘阵图库检索，逐条返回场景元数据，并补充 `W/H`（优先读取伴生的 `.hdr` ENVI 头；缺失时探测 TIF 头并做 LRU 缓存）+ `jpgUrl`（nginx 静态地址；未生成时为 null）。
- `GET /api/scenes/{id}/preview`：**按需生成（lazy generation）**——若 JPG 不存在或早于源文件，先在服务端生成一张再返回；生成后落盘，后续由 nginx 静态直出。

场景 id 使用 `base64url(相对路径)` 作为不透明标识：前端只持有 id，不接触也不应知晓盘阵绝对路径。

### 7.3 路径白名单：必要性及实现

后端暴露盘阵文件，首要风险是构造 `../` 或绝对路径访问白名单外文件。安全实现（[backend/api/paths.py](backend/api/paths.py)）：

- 所有返回/生成的路径经 `realpath` 后必须位于场景根目录内；拒绝 `..` 目录穿越、白名单外绝对路径与 `<fake>` 占位路径。
- scene id 解码时补回 `=` 填充、拒绝非法 id、再次以 `realpath` 校验。
- **fake 数据一律不得用于生成预览**——开发机上可产生假数据，真机上绝不能因此访问真实文件。

> 通用原则：**凡对外部暴露"文件/命令"能力，第一件事是划定可访问边界，并在边界上拒绝一切越界输入**。`run_sr` 同理：`lq_path`/`mask_path` 必须为绝对路径且不含 `<fake>`。

### 7.4 同构 rec：掩码与缩放逻辑全量复用

盘阵场景打开的影像与本地路径打开的影像，内部均构造成同一种 rec（route = `'jpg'`）。区别仅在：

- `src` 来自 JPG 画布像素，且 `stats` 固定为 0..255 → 任何交互拉伸都退化为恒等映射，不会对服务端已完成的 2% 拉伸重复处理（`paintStretch` 对 jpg 直接返回）。
- 掩码换算回全分辨率时，`scale` 使用**服务端返回的元数据 W/H**，而非本地探测 TIF。

收益：平移、缩放、绘制掩码、合并、删除等交互**全量复用**，前端未为盘阵单独编写交互逻辑——这是"算法层 / 状态层同构、仅数据来源不同"带来的复用效果。

### 7.5 前后端各实现一份的镜像常量（修改需双向同步）

服务端生成 JPG 所用的采样与拉伸语义，必须与本地路径在视觉上一致。因此后端 [preview_jpg.py](backend/services/preview_jpg.py) **镜像前端**的映射：

- 稀疏采样：目标列 `round(j*(W-1)/(pw-1))`（端点对齐，避免右/下边缘条纹——此前使用 `ceil` 导致最右列像素重复的缺陷）。
- 拉伸：2% Linear；WhiteIsZero 先反色；常量影像退化为"全 0 → 黑，其他常量 → 128"。
- 仅读取采样行所在的条带（大影像不整幅载入，服务端内存与 1.78GB 影像尺寸解耦）。

**同一组常量在前后端各实现一份，改动任一端必须同步另一端并运行两端单测**——该约束已写入经验文档。此类双实现易逐渐漂移，依赖像素对照测试锁定一致性。

> **本节向上汇报**：阶段 4 引入后端 FastAPI，盘阵场景改为读取服务端按需预生成的 8192 预览 JPG，浏览器不再接触原始大影像，从机制上规避内存与画布上限；本地文件路径保持原读取方式，行为不变。已交付场景检索、预览按需生成与路径白名单安全校验，并以镜像常量 + 像素对照测试保证服务端与本地端影像显示一致。

## 8. 阶段 5：平台 API 层 + 聊天 / 共享队列（进行中）

> 状态说明：本节描述的契约处于**评审阶段**（见 [docs/planning/api-contract.md](docs/planning/api-contract.md)），代码尚未落地。理解"做什么、为何这样设计"即可，细节以定稿契约为准。

阶段 1~4 已有 Agent（`backend/agent`）、4 个工具、任务幂等表、Slurm 客户端——但目前仅经命令行调用（`python -m backend.agent "..."`）。阶段 5 的目标是将它们暴露为网页可调的 REST/SSE 接口。

### 8.1 Agent 是自写的状态机，而非黑盒

后端 Agent 核心 [backend/agent/loop.py](backend/agent/loop.py) 是一个自写的循环：将用户消息与"工具清单"交给大模型，由模型决定"是否调用工具、调用哪个、参数为何"；当模型要求调用时 → 执行工具 → 将结果返回模型 → 模型再次回复，如此迭代直至模型给出最终答复。

工具采用**注册表**模式（[backend/tools/contract.py](backend/tools/contract.py)）：每个工具通过装饰器声明名称、描述、参数 JSON Schema 及一个 `run(**params) -> {ok, data, error}`。注册表可自动导出 OpenAI 兼容的工具清单——**同一份清单既供大模型 function calling 使用，又用于生成面向网页的 REST 端点**（阶段 5 的 `/api/tools/{name}`）。

首批 4 个工具：`search_scenes`（检索盘阵）、`run_sr`（向 Slurm 提交超分作业）、`sr_job_status`（查询作业状态）、`fix_bad_lines`（坏行修复，真实影像处理工具）。

> 不引入 LangChain 的原因：流程较短（消息往返 + 工具分发 + 迭代上限），自写实现可读、可测；引入全家桶反而需要额外学习一套框架。当未来出现"跨小时断点续跑、人工审核"等需求时，再评估加入 LangGraph 薄封装。

### 8.2 mock LLM：无真实模型时如何验证完整对话

Agent 依赖大模型，但开发机未配置模型端点、也不希望每次测试联网。处理方法：为 LLM 调用层预留注入点（`_default_chat`），并增设环境开关 `SR_LLM_MOCK=1`——开启后返回**固定脚本的假 chat**：先声明调用 `search_scenes`（离线环境下同样返回真/假数据），再输出一句总结。由此：

- 网页聊天**不依赖任何模型**即可演示完整的"调用工具 → 返回结果 → 总结"循环；
- 端到端测试可**确定性地**断言 SSE 事件序列（tool_call → tool_result → turn_done）。

红线：mock **仅替换 LLM 调用层，不改动状态机逻辑**——loop.py 的行为仍由既有 18 个测试固定（约束 3 的方法论：替身只替换"外部那一层"）。

### 8.3 SSE：让网页实时看到 Agent 的执行过程

Agent 执行一轮需数十秒，用户无法等待同步返回。采用 **SSE**（Server-Sent Events，服务端推送事件）将过程实时推送给网页：

```
POST /api/chat/sessions/{id}/messages     ← 前端发送一条消息
响应为 text/event-stream，每帧一行 data:{json}\n\n：
  {"type":"turn_start",   ...}
  {"type":"tool_call",    "name":"run_sr","args":{...}}
  {"type":"tool_result",  "name":"run_sr","ok":true,"data":{...}}
  {"type":"turn_done",    "content":"已提交作业 12345"}
（预留 {"type":"token","delta":"…"} 供后续 token 流式渲染）
```

契约中的实现要点：

- **POST 请求即事件流**：一次请求对应一回合，请求的响应体即 SSE 流。同步的 `run_loop` 为阻塞调用，需移入线程池执行，事件经 `asyncio.Queue` 桥回主协程逐帧下发。
- **同一会话同一时刻仅允许一个回合**（并发请求返回 409"会话正忙"）——消息存在顺序，不允许并发写入同一对话。
- **前端不能使用 `EventSource`**（其仅支持 GET），须用 `fetch` 发送 POST 后自行读取 `response.body` 流并切分 SSE 帧。为此将实现一个可单测的帧解析器。
- **聊天会话 = 单会话 + 「新建」操作**，持久化至 SQLite：刷新页面可从历史恢复，切回旧会话可继续（复用 loop 既有的 resume 语义）。

### 8.4 共享队列：任务表 + 幂等 + 状态机

网页提交一个 SR 作业即调用后端 `submit_run_sr`（[services/run_sr.py](backend/services/run_sr.py)），其流程：

1. 将高层参数（`lq_path`/`mask_path`/`sr_scale`/`gpu`/`cloud_limit` 等）拼装为 `config.xml` 与一个 Slurm 批处理脚本；
2. **先查询 `sr_tasks` 幂等表**（按参数指纹）：同参作业已在运行或已完成 → **复用该作业，不重复提交**（返回 `RESUMED_*`）；仅当失败或状态未知才重跑；上次提交被中断（无 job_id）→ 明确报错提示"勿盲目重试"；
3. 执行 sbatch 提交 → 记录 job_id。

网页队列页（`/queue`）：

- 列出全部任务及实时状态。状态来自后台一个**校准器**周期性对活动任务执行 `squeue/sacct` 查询（Slurm 自身会变更状态，服务端不轮询即无法感知）；状态变更经 `/api/queue/events` 的 SSE **广播**给所有在线网页。
- 状态为状态机而非百分比：`SUBMITTING → PENDING → RUNNING → COMPLETED/FAILED`。

> 假 Slurm 的离线测试价值：开发机没有 sbatch。规划加入 `SR_SLURM_FAKE=1` 的内存假调度器——`config.xml`、脚本、幂等表**全部走真实逻辑**，仅将"squeue/sacct 的返回"替换为可配置推进的假结果。与 §7 场景 fake 属同一方法论。

### 8.5 查看器完成掩码 → 提交 SR

闭环最后一步：查看器在影像上圈定区域后"一键提交超分"。掩码栅格化（全分辨率 0/255）为较重操作且需在盘阵机落盘，规划流程为：

1. 查看器将多边形（已按元数据 W/H 换算回全分辨率）与场景 id POST 至 `/api/masks`；
2. 后端栅格化掩码并写入**原影像所在目录**：`<原图目录>/<stem>_mask.tif` + `_mask.txt`（约定：掩码与超分结果均落在原影像同目录）；
3. 返回 `mask_path` 与 `lq_path`，前端以其**预填队列表单**，用户点击「提交」后才真正提交（Slurm 提交为真实副作用，不自动触发）。

> **本节向上汇报**：阶段 5 处于契约评审阶段、代码尚未开发。目标为将既有 Agent、工具注册表、任务幂等表与 Slurm 客户端暴露为 REST/SSE 接口，支撑聊天与共享作业队列两个页面；关键技术点已明确——mock 仅替换 LLM 调用层以保证可离线验证，SSE 以"POST 请求即事件流"实现，作业提交以参数指纹幂等表防止重复，队列状态由校准器轮询并经 SSE 广播。

## 9. 横向主题一：状态管理 —— Pinia store 的职责边界

**何时需要共享 store**（本项目三条均命中）：

- 多个页面/组件需读取**同一份数据**（查看器画布、队列任务）；
- 状态**可被多方修改**，修改后其他方需感知（多人队列、当前激活影像）；
- 存在**异步与并发**，状态变更顺序可能错乱（解码进度、SSE 事件到达）。

**Store 的三种职责模式**（本项目均使用）：

| 模式 | 示例 |
|---|---|
| **服务端状态缓存**：从后端拉取并在本地保留副本 | `stores/scenes.ts` 拉取 `/api/scenes` |
| **本地重型状态 + 操作**：集中调度复杂交互逻辑 | `stores/viewer.ts`（影像列表 / 视图 / 掩码 / 导出） |
| **SSE 事件归并**：事件流 → 合并入状态 → 触发渲染 | `stores/chat.ts` / `stores/queue.ts`（阶段 5 占位） |

**乐观更新 + 回滚**：交互先按预期结果立即刷新界面（提升响应感知），请求失败时回滚。其前提是**服务端为唯一事实源**（多人队列尤甚），前端缓存随时可被刷新覆盖。

**数据流示意**（以阶段 5 队列为例）：

```
后端 Slurm 状态变化
  → 后台校准器轮询 → 状态变更
  → SSE 广播 job_update 事件
  → 前端 fetch 流读取事件
  → queue store 更新 job.status
  → Vue 响应式重新渲染列表行
```

> **本节向上汇报**：状态管理采用 Pinia，以"跨组件共享、多方修改、异步并发"三项标准界定 store 职责；交互层采用乐观更新并以服务端为唯一事实源。本项目三种 store 模式（服务端状态缓存、本地重型状态、SSE 事件归并）均已规划落地。

## 10. 横向主题二：三层测试各测什么

> 仓库存在多套测试体系，各层测试对象不同、互不替代。明确分工可显著减少试错时间。

| 层 | 工具 | 测试对象 | 归入该层的原因 |
|---|---|---|---|
| **前端单元（纯函数）** | Vitest | 像素级解码/拉伸/掩码对照、URL 拼装、SSE 帧解析 | 纯函数无副作用、执行快、可断言"每个像素的值" |
| **后端测试** | pytest | 流程逻辑 + **注入假依赖**：假 slurm 命令、假 LLM、假场景、临时 SQLite | 测试编排逻辑而非真实系统；对外副作用均可注入 |
| **浏览器端到端** | puppeteer-core + 无头 Edge | 真实页面加载、点击、真 canvas 出图、route 接线 | 仅真实浏览器可覆盖"组件 ↔ store ↔ 画布"的接线 |
| **类型检查** | `vue-tsc --noEmit` | 全前端类型正确性 | TypeScript 项目的基础保障 |

**测试方法论三条原则**：

1. **能测纯函数就不放浏览器层**：掩码栅格化等像素逻辑置于 Node 中逐像素断言，不放入 e2e。
2. **为外部副作用保留注入点**：命令行执行器、LLM 客户端、调度器、数据库路径均可替换为假实现（对应约束 3 的替身方法）。
3. **以基线对照断言结果**：验证"已知输入 → 每个像素的期望值"，而非"结果大致变亮"等主观判断。

> 浏览器 e2e 存在已知问题：无头浏览器可能异常退出但退出码为 0、无任何错误输出。仓库解法是为每次运行创建**独立的临时浏览器配置目录**（见 [.e2e/launchBrowser.js](.e2e/launchBrowser.js)），避免浏览器单实例目录锁。
>
> **本节向上汇报**：测试体系分四层——前端纯函数（Vitest）、后端流程（pytest + 注入假依赖）、浏览器端到端（无头 Edge）、类型检查（vue-tsc）。方法论为：纯函数优先、外部副作用可注入、断言基线像素而非趋势。当前后端与前端用例均可离线全绿。

## 11. 横向主题三：内网离线部署

部署形态：**内网 CentOS7 盘阵机**上运行 nginx + 一个 FastAPI 进程（systemd 托管），网页为 nginx 托管的静态产物。环境需完全离线安装，因此依赖清单须显式声明。

### 11.1 环境变量是唯一的配置入口

后端所有可变配置均从环境变量读取（[backend/config.py](backend/config.py)）：场景根 `SR_SCENES_ROOT`、预览缓存 `SR_PREVIEWS_ROOT`、LLM `SR_LLM_*`、Slurm `SR_BUNDLE_DIR` 等。因此**同一份代码在开发机（fake）与生产机（disk）之间通过切换环境变量即可复用，无需改动代码**。systemd 单元中将 env 固定，见 [deploy/sr-api.service](deploy/sr-api.service)。

### 11.2 nginx 的三个职责

1. **托管前端静态资源**：`/` 指向前端构建产物，SPA history 路由需配置"文件未命中时回退 `index.html`"。
2. **反向代理 `/api/` 至 `127.0.0.1:8000`**：前端同源请求 `fetch('/api/...')`，由 nginx 转发至 FastAPI。
3. **托管盘阵 JPG 静态资源**：`/disk-array/` alias 至场景目录——预览 JPG 生成后由 nginx 直接返回（利用其原生缓存，性能最优），不经过 Python。

**SSE 配置要点**：nginx 默认缓冲代理响应，而 SSE 需要持续向客户端推送，须对相关 `/api/` 路径关闭缓冲并放宽读超时：`proxy_buffering off; proxy_cache off; proxy_read_timeout 3600s;`——否则网页收不到逐帧事件（见 [deploy/nginx.conf](deploy/nginx.conf) 与契约 §6）。

### 11.3 交付物中为何常含"真机验收项"

受约束 3 限制（开发机无法访问真实数据、无真实 Slurm），开发机上可离线自证的是：pytest + Vitest + e2e（使用假后端/假调度器）+ 部署件。**真机项单独列为验收清单**（首次预览生成耗时、真实 Slurm 提交、真实模型调用），标注"需在 CentOS7 / 内网执行"。这是交付边界的明确划分：可自动化的全部自动化，无法在开发机验证的以清单形式交由真机验收——其原因是外网开发机物理上无法执行，而非疏漏。

> **本节向上汇报**：部署形态为内网单机 nginx + systemd 托管的 FastAPI；全部可变配置集中于环境变量，同一份代码在开发与生产环境间仅需切换环境变量即可复用。nginx 承担静态托管、API 反代与盘阵预览图直出三项职责，并对 SSE 路径关闭代理缓冲。开发机无法执行的验证项（真实数据访问、真实作业调度、真实模型调用）已单列真机验收清单。

## 12. 动手清单（验证路径 + 联动红线）

推荐的验证顺序：

1. **运行现有测试**建立基线：后端 `python -m pytest backend/tests -q`、前端 `npm test` + `npm run typecheck`。
2. **启动本地后端** `python -m backend.api`（未设 `SR_SCENES_ROOT` → 自动启用 fake），`curl /api/health`、`/api/scenes` 查看返回。
3. **启动本地前端** `npm run dev`，打开 `/viewer`（拖入 `frontend/fixtures/` 中的小 TIF）与 `/scenes`。
4. 从一个小改动入手（如为列表增加一列），按"改 lib 纯函数 → 跑 Vitest → 接线 store/组件 → 跑 typecheck/e2e"的顺序推进。

**改动时的联动检查清单**（仓库中最易遗漏的关联）：

| 改动对象 | 必须同步 | 红线 |
|---|---|---|
| 前端拉伸/稀疏映射常量 | 后端 `preview_jpg.py` 镜像逻辑 + **两端单测** | 改一端必须同步另一端 |
| REST / SSE 契约（端点、字段、事件） | 先改 `docs/planning/api-contract.md`，再改代码 | **契约文档先于代码** |
| 掩码填充/产物约定 | 前端 `maskgen.ts` 与后端 `mask.py` | 必须逐像素一致 |
| vendor 库 | 无 | 补丁版 `utif.js` 不得重新安装 |
| 后端运行依赖 | `deploy/requirements-api.txt` | `openai` 锁 `>=1.40,<2`（aiohttp 3.8.3 不兼容 3.x） |
| 数据源测试替身 | 防止 fake 路径进入真实消费端 | `<fake>` 一律拒绝 |

**贯穿全文的三条设计原则**：

1. **大对象不整幅读取，采用分块或抽样读取**——浏览器 2GB、Canvas 16384² 的限制始终存在。
2. **将重处理放在数据所在机器执行**——盘阵预览 JPG 由盘阵机生成，网页只读取结果。
3. **真实系统不可达时，构造显式标记、可被拒绝的测试替身来验证**——替身只替换外部依赖层，自身逻辑照常运行。

> **本节向上汇报**：当前可交付的验证口径为 pytest + Vitest + 端到端（假依赖）+ 部署件全部通过；真实环境项（首次预览生成耗时、真实 Slurm 提交、真实模型调用）已单列真机验收清单，待内网执行。代码改动遵循四条红线：双端镜像常量须同步、契约文档先于代码、掩码产物逐像素一致、补丁版 vendor 库不得重装。
