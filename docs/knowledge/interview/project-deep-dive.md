## 1. 三十秒开场稿（背到脱口而出）

> "我做的是一套**遥感影像超分平台**，给卫星影像做超分重建的科研/工程团队用。核心是**在浏览器里流畅查看单张 2 万多像素的 16bit 大 TIF**——直接受浏览器内存上限(单次分配约 2GB)和 Canvas 面积上限(16384²)约束——所以我解了一条**从数据形态到展示的链路**：先摸清真实文件是"无压缩+每行一个条带"，据此做**稀疏条带采样**(整图解码 4.5s → 秒级)、再在前端画 ROI 掩码、后端用 Slurm 队列把超分作业提交到 GPU 集群。
> 项目从**纯前端单文件查看器**一路长成**前后端平台**：一个 Vue3+TS 查看器，一个 FastAPI 后端把"Agent 循环 + 4 个工具 + 任务表 + Slurm 客户端"暴露成 REST/SSE。全程**只支持 Chrome/Edge、离线可用、第三方库全部本地内置**，因为部署环境连不上 CDN。
> 开发机是外网机、真实大图全在内网盘阵读不到，所以我把"真实系统进不来"这件事变成了方法论：**用 env 开关造显式标记的假数据/假后端**，同一份代码零改动跑通 dev(假) 与真机(真)。单测前端 85 + 后端 148 + 浏览器端到端 45 断言全绿。"

**挑着背的子弹（每个都能撑住一分钟追问）：**
- 真实文件 = GF07A03(1.11GB) / KF02B04(1.78GB)，24739×24199 级，单波段 16bit，**无压缩、每行一个条带** → 不用金字塔，任意窗口按字节切片。
- 134MB 8192² 测试图：稀疏预览 **1.3s**(只读 32MB/128MB) vs 全量解码 **4.5s**；真实 1.1GB 图预计从 ~2 分钟降到秒级。
- 浏览器单次分配上限 ~2GB、Canvas 16384² → 大图全量解码必崩 → 三路解码分派。
- 阶段4 让浏览器**不再读盘阵原始 TIF**，改读服务器预生成的 8192 长边 JPG(懒生成、幂等缓存)。

## 3. 难点问答（高频，每条挂真实文件/数字）

### A. 大图解码与浏览器限制

1. **Q：为什么浏览器看不了你的遥感大图？难点在内存还是别处？**
   **A：** 三层约束叠加：① **单次 TypedArray 分配上限 ~2GB**(Edge 实测 2.0GB 成功、2.7GB RangeError，与机器 64GB 内存无关)——30000² RGB8 整图解码要 2.7GB+，必崩；② **Canvas 面积上限 ~16384²**；③ **CDN 不可达**，第三方库得本地内置。
   - 所以我给解码做**分派**(`lib/decode.ts` 的 `needGeo`)：小 8bit → UTIF 整图；大/压缩/tiled → geotiff.js 分块；**无压缩+条带+单波段+>100MB → 稀疏采样**。
   - 🗂 数字：真实文件无压缩、每行一条带，才让"稀疏 + 字节切片"成立(不需要金字塔)。`SAFE=1.3e9` 内存护栏。
   **追问：** 全量解码为什么会死？→ 不是慢是分配失败；分块/稀疏都为了把"单次大分配"拆小。

2. **Q：稀疏条带预览的原理？为什么这么快？**
   **A：** 真实 TIF 无压缩，字节偏移可算，等于可以**随机读任意行**。
   - `parseStrips` 解析头，读出每条 strip 的偏移/长度数组(兼容 classic/BigTIFF)；
   - `sparseSample` 只**每隔 ph 行抽 1 行、每行只留采样列**(8 路并发)，预览长边 8192；134MB 8192² 图只读 32MB/128MB → **1.3s** vs 全量 4.5s。
   **追问：** 采样映射为什么用 `round(j*(W-1)/(pw-1))` 而不是 `floor(j*W/pw)`？→ Bug C 教训：用 ceil+clamp 会让右/下边**重复最后一列像素、拉出条纹**；"目标→源"端对齐才能让两端像素精确重合。

3. **Q：你踩过哪些解码黑屏/白屏的坑？挑两个讲。**
   **A：**
   - **400MB 全黑**：UTIF 的 `toRGBA8` 只支持每采样 1/2/8/16 bit，32bit 数据落空变全 0 → 自己实现按 bps 的拉伸；
   - **16bit RGB 半透明全黑**：alpha 通道被亮度拉伸系数 scale≈0.0039 缩到 0 → 修：**alpha 永不做拉伸**、通道<4 强制 255；
   - **WhiteIsZero 反色**：photometric=0 表示"白=0"，没反色就颜色反转(单波段遥感常是 WhiteIsZero)。
   **追问：** 为什么有两套引擎？→ UTIF 解不了 BigTIFF(BigTIFF 的 tag 是 64bit 偏移)；大/压缩走 geotiff.js 分块。`needGeo` 探测到 `probe.big` 强制走分块。

4. **Q：为什么导出/预览都停在 8192 而不上 16384？**
   **A：** 8192 长边 ≈ 原图 1/3，够网页显示；16384 会顶到 **Canvas toBlob 面积/内存上限**。8192 导出失败自动**降档重试 4096**(`_exportCap`)。预览 JPG 与导出 JPG 用同一套拉伸与映射，两处所见一致。

### B. 掩码（前端直出，几何精度）

5. **Q：掩码为什么能在浏览器直出 TIF？全分辨率栅格化不卡吗？**
   **A：** 掩码只管"某像素处不处理(0)/处理(255)"，是**几何问题**，不受亮度拉伸/有损 JPG 影响——所以可在 8192 预览上画、换算回全分辨率。
   - 全分辨率栅格化**按行流式**(`rasterRows` 逐行产事件，不一次性建整图位图)+ pako Deflate → 内存只随压缩缓冲走；
   - 合并连通区时每个区域只在**自己的最小外接矩形子图**里重扫，不再整图新建 65MB 数组；
   - 产物像素值 0/255 与后端 Pillow 版**逐像素交叉验证一致**(前后端两套实现互锁)。
   **追问：** 换算精度怎么保证？→ `thumbToOrig` 按预览分辨率→元数据 W/H 比例换算，画完再用 E2E `buildMaskJson` 反算校验；阶段4 起掩码落点按元数据 W/H(见 §C)。

6. **Q：魔棒/合并/删除，这些"抠图"功能难在哪？**
   **A：**
   - **魔棒自适应区域生长**：固定容差对比种子会把有纹理/渐变的地物切碎。改用种子 7×7 窗口初始化均值/平方和，生长窗口 = `max(tol, 2.5*spread)`，增量重算(每 256 像素)，边缘亮度屏障 `WAND_EDGE` 单独挡住，`WAND_MAX_PX=8e6` 防失控；
   - **合并重叠**：1px 外扩 → 并集栅格化 → 填洞 → 按连通区(BFS)重追踪轮廓 → 缩回 1px；分批 yield 进度让主线程不卡；
   - **删除**：命中检测(射线法)后 200ms 红闪再删，**异步防误删**(记 `owner`，期间切图就跳过)。

### C. 阶段4：后端读 JPG 的转向

7. **Q：阶段4 你为什么让浏览器"不再读盘阵原始 TIF"？**
   **A：** 三个理由把 HttpSource+Range 方案推翻了：
   - 与"预览=JPG 中间产物"的已有决策对齐(掩码已按 JPG 换算)；
   - 浏览器 2GB / 16384² 预算扛不住盘阵全分辨率原图；
   - 服务器一次性烘焙、nginx 静态直出 + 缓存头，比浏览器反复 Range 读高效。
   - 代价讲清楚：**网页内看超过 1/3 细节的需求被放弃**，细节看 JPG 产物或原文件。
   **追问：** 那掩码精度不受影响？→ 掩码几何只依赖分辨率，8192≈原图 1/3 够粗画，换算回全分辨率落点由后端元数据 W/H 保证。

8. **Q：`/preview` 怎么保证大文件不把后端内存吃爆？**
   **A：** 逐条带抽读：先解析头拿条带偏移，**只碰采样行、每行只留采样列**，绝不整图载入；采样映射 `round(j*(W-1)/(pw-1))` 与前端**逐像素同语义**，保证"前端拉伸预览"和"后端烘焙 JPG"一致。
   - 亮度拉伸：2% Linear(取 1%/99% 分位做 min/max)+ WhiteIsZero 先反色 + const 图规则(全 0→黑、其他 const→128)；
   - 幂等：落源同目录 `<basename>.preview.jpg`，二次请求直接 FileResponse。
   - 压缩/tiled/多波段小文件走 Pillow 兜底；大文件不支持则明确报错，不假装能处理。
   **追问：** 前后端两套拉伸实现会不会漂移？→ 这是红线：常量(分位百分比/映射公式)写在同一处、两侧测试都锁(阶段4 用 stats 固定 0..255 使 JPG 路线拉伸恒等来消歧)。

9. **Q：为什么"能读任意文件/路径"的接口第一件事是白名单？**
   **A：** 端点能读盘阵文件 = 面向外部的读能力。不拦 `../` 穿越、白名单外绝对路径、伪文件路径，等于把盘阵目录交出去。
   - `paths.py`：`realpath` 后必须**含于场景根**；场景 id 用 base64url(相对路径) 做成**不透明 id**，前端根本不接触盘阵绝对路径；
   - `<fake>` 占位(开发机假场景)永不允许当真生成预览/提交；
   - 越权访问返回 403/404，`journalctl` 可审计。

### D. Agent 循环与工具

10. **Q：Agent 循环你自己写，为什么不用 LangChain？**
    **A：** 需求是"调工具 + 给结果"的最小闭环，用 LangChain 全家桶是杀鸡用牛刀、还引一堆依赖(环境连 CDN/离线受限)。自己写约 200 行状态机(循环上限 + 工具传参出错自动纠正重试 + 未知工具处理)。**边界讲清楚**：等真遇到跨小时断点续跑/人工审核，再按边界上薄 LangGraph，只是替换薄层不是重写(仓库有 `docs/conventions/langchain-boundary.md` 定边界)。

11. **Q：工具怎么声明？"接口约定"指什么？**
    **A：** `contract.py` 的 `@tool` 装饰器 + 注册表：每个工具声明 name/description/JSON-schema params，`manifest()` 能导出**OpenAI 兼容函数清单**——同一份注册表既喂给 function-calling、又能自动生成 API 文档。
    - 返回统一 `{ok,data,error}`：**业务失败不抛异常**，模型读到 error 自我修正参数重试(如 `lq_path` 含 `<fake>` → 回填真实路径重试)。
    - 分层：`tools/`(薄壳) → `services/`(流程编排) → `mta_grid/`(纯算法)，同一份 services 被 REST/CLI/Agent 三处复用。

12. **Q：run_sr 幂等是什么意思？为什么必须有？**
    **A：** run_sr 是**提交 Slurm 外部作业**的副作用：网络/进程随时断，用户/Agent 会重试。若每次 POST 都真提交，重放 = Slurm 上**多一个重复作业、白烧 GPU**。
    - `sr_tasks` 表存 `job_id` + 参数 **sha256 指纹**；`submit_run_sr` **先查表再提交**：已有 job_id 且 active/COMPLETED → 直接复用返回 RESUMED_*(不重复提交)；FAILED/UNKNOWN 才重跑；上次提交被中断(有意图无 job_id) → 明确报错**不盲目补提交**；
    - 落库时机 = **副作用前先记意图**(checkpoint)：崩溃也只留一个可修复的"未完成回合"，恢复时生成"上次结果未知、别盲重试"提示、不重执行工具(借鉴 deepseek-harness 语义)。

13. **Q：Slurm 客户端怎么测试？本机没有 sbatch 怎么办？**
    **A：** 命令执行器 `run_cmd` **可注入**：测试用假 `run_cmd` 断言"发了哪条 sbatch / squeue / sacct / scancel"，不真起作业；本机没 sbatch → 返回明确错误，绝不误以为 SR 跑起来了。
    - 状态轮询：先 squeue 看在不在跑，结束后 sacct 拿最终状态 + 退出码；`slurm_available()` 探活。
    **追问：** 真机怎么配？→ env：`SR_BUNDLE_DIR/SR_PYTHON/SR_SLURM_WORK_DIR/SR_SLURM_PARTITION`。

### E. 前端架构与测试

14. **Q：Vue3 迁移为什么叫"移植不重写"？价值在哪？**
    **A：** 旧单文件 HTML 已踩完所有解码/拉伸/稀疏读取的坑(116KB)。直接 import 那些**与框架无关的 TS 模块**(`lib/`)逐字节保留，只把交互层改成 Vue3 惯用写法——解码算法的黄金对照测试一次不重写、像素级回归始终在。
    - 组件化：TifCanvas/Toolbar/FileList/DrawPanel/DecodeOverlay/StatusBar 六组件 + `stores/viewer.ts` 统一调度 + `renderTick` 计数触发重绘(等价旧 `render()`)；
    - 大对象字段用 `markRaw`/`shallowRef`，避免把整块像素数据拖进响应式。

15. **Q：两条数据源(本地 File / 盘阵 HTTP)怎么统一？**
    **A：** 解码层抽统一 `source.read(offset,len)→Promise<ArrayBuffer>`：本地走 FileSource、盘阵本应走 HttpSource+Range——**但阶段4 把盘阵路径改掉了**：HttpSource 桩废弃，盘阵场景只 `<img>`/canvas 加载服务器烘焙 8192 JPG(route='jpg' 同构 rec)。IFD/稀疏/拉伸逻辑两端共用；本地文件路径零改动。

16. **Q：测试分几层？各锁什么？(把数字背熟)**
    **A：**
    - **像素级黄金对照**(Vitest，Node)：解码/掩码输出与参考逐像素比对，防移植漂移；
    - **后端 pytest 148**(当前)：解码服务/掩码 txt 逐字节对齐/幂等/白名单穿越/预览缓存；
    - **浏览器端到端**(`.e2e/`，puppeteer-core + 无界面 Edge)：真实页面行为——`test-scenes.js` 45 断言(静态服务顶替 nginx + 真 uvicorn 起后端)、`test-vue-viewer.js` 42 断言(本地文件回归)；
    - 大图/真机必须内网盘阵，dev 侧用假数据 + env 开关(见 §F)。
    **追问：** e2e 最坑的是什么？→ 无界面浏览器"退出码 0 闪退"，根因是 Edge 配置目录单实例占用 → 每次用独立临时 profile 目录。

### F. 假系统方法论(本仓库特色，必讲)

17. **Q：开发机读不到真实数据，你怎么保证"真机上能跑"？**
    **A：** 方法论 = **真实系统进不来，就造"显式标记"的替身，替身与真身同接口，env 开关切换，默认给假的**：
    - `SR_SCENES_ROOT` 没设/不存在 → 返回**带 `fake:true` 的假数据**，路径占位 `<fake>/...`；假路径被白名单/工具层拦截，**永远流不进真实消费端**；
    - `SR_SLURM_FAKE=1` → 内存 fake 调度器；`SR_LLM_MOCK=1` → 固定脚本假 LLM(规划)；
    - 真机接入 = 把 env 指到真挂载点/真端点，**代码零改动**。这叫"dev 侧闭环可测，prod 只换配置"。
    **追问：** 有没有照进真机才发现的问题？→ 诚实弱点，见 §4。

18. **Q：openai 版本为什么锁 `>=1.40,<2`？**
    **A：** 真机 aiohttp 3.8.3 与 openai 3.x 不兼容(装 1.109.1 可用)。**依赖版本要跟着目标环境的真实约束走**，不是跟着最新走。

### G. 阶段5(规划/评审中——答"我打算怎么做")

19. **Q：阶段5 把 agent 暴露成聊天接口，最难的是什么？**
    **A：** 一个回合可能几十秒(工具循环 + 模型推理)，而 HTTP 响应要**边跑边推**给前端。
    - 选型：EventSource 只支持 GET，POST 即流用不了 → **前端用 fetch 读 body 流**，后端 SSE `StreamingResponse` 逐帧 `data:{json}\n\n`；
    - **同步阻塞的 run_loop 用 `asyncio.to_thread` 丢线程池**，事件经 `asyncio.Queue` 桥回主协程逐帧下发——否则一个慢回合会卡死整个事件循环、拖死所有 SSE 连接(这是我会重点讲的坑)；
    - 同会话并发：会话级锁串行，忙则 409。
    **追问：** 契约里事件 schema 有哪些？→ `tool_call/tool_result/turn_done`，预留 `token`(token 类型字段定了但 MVP 不实现)。
20. **Q：为什么阶段5 强调"契约先行"、单独一份 `api-contract.md`？**
    **A：** REST/SSE 是前后端**共享接口面**：前端 parser 和后端 emitter 必须对同一 schema。契约文档先落盘 = 字段/事件/错误码/状态机先说死；改契约先改文档再改两端，各留测试锁字段。流程 = 我评审契约 → 后端 → 前端 → 双端测试。

21. **Q：SSE 的队列状态怎么保证真实？进程内广播够吗？**
    **A：** 后台 reconciler(asyncio 周期任务)轮询 Slurm 更新 `sr_tasks`，再通过**进程内 pub/sub**(一组 asyncio.Queue 存在线 SSE 连接)广播。
    - 边界：这只在**单 worker**内成立；将来多 worker 需外部队列(Redis pub/sub)跨进程广播。**能力边界写清楚 = 加分不是减分**；
    - 部署注意：nginx 反代 SSE 要 `proxy_buffering off` + `proxy_read_timeout` 调大，否则逐帧被攒缓冲、长连接被掐。

## 4. 追问防守与诚实弱点（每句都要能自圆）

> 面试官最常打的点 = **"这些数字是不是编的"**。防御姿势：主动给文件路径 + 说明验证环境。

| 弱点 | 话术 | 补强 |
|---|---|---|
| **真机未验收** | "阶段4 后端 148 pytest + e2e 45 断言在开发机全绿，但真实 1.1GB/1.78GB 图的首烤耗时/内存还在内网盘阵等验收，我有现成验收清单(测首烤、幂等缓存、进程 RSS、`../` 越权 403)" | 知道验收的**每一项测什么、预期什么**，比"都测过"可信 |
| **真实文件结构靠回传** | "开发机是外网机，读不到内网盘阵；文件结构是让用户回传 ENVI 头信息确认的——GF07A03/KF02B04 都是无压缩+每行一个条带" | 说清"结论从哪来"，暴露推理过程 |
| **前端"查看超 1/3 细节"被放弃** | "这是明确取舍不是缺陷：8192 JPG ≈ 1/3 够网页用；细节看 JPG 产物或原文件。以后要网页全分辨率，无压缩条带下仍可直接字节切片捡回，不需要金字塔" | 取舍有文档、旧方案没丢 |

| **SSE 单 worker** | "进程内广播设计成单 worker；真多人并发再接外部队列" | 知道代价与升级路径 |
| **前后端拉伸双实现漂移** | "常量同源、两侧测试都锁、JPG 路线用固定 stats 消歧——这是跨阶段红线，出过同步疏漏教训，现在用测试兜" | 承认风险 + 给出控制手段 |

## 5. 反问清单（结尾问面试官，挑 1~2 个）

1. "你们在用的遥感/图像数据，单张最大到多大、浏览主要在什么端？" —— 试探对方是否也踩过浏览器大图。
2. "超分/图像处理的 GPU 是怎么调度的？" —— 试探是否有 Slurm/队列场景，你刚好有经验。
3. "平台是内部工具还是对外产品？数据在内网吗？" —— 判断离线/安全约束是否和你的方法论契合。

## 一句话备忘
> **讲项目 = 一条"数据形态→浏览器限制→解码/掩码→后端服务→平台化"的因果链；每个技术点对应一个真实文件 + 一个真实数字；主动讲"取舍与未验收"，比背一套完美履历更稳。**
