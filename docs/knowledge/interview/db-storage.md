## 一、关系型基石：ACID / 隔离 / 锁 / MVCC

### 1. 关系型 vs NoSQL 怎么选？★

- **答（要点）**：关系型（MySQL/PostgreSQL/SQLite）靠**表结构 + 外键 + 事务 ACID + 标准 SQL**，适合**强一致、结构化、需要联表/聚合、要跨行事务**的数据（订单、用户、账务）。
- NoSQL 是"**为某类读写专门优化**"的泛称，不是同一种东西：Redis（内存键值/缓存/热数据）、MongoDB（文档/半结构化/字段多变）、ES（全文检索/聚合分析）、Cassandra（海量写入/水平扩展）。
- **选型口诀**：先问三件事——**要不要事务与强一致？要不要 Join？读写模型是否固定、单机能否扛住？** 前两个是"是"，就选关系型；NoSQL 的正当理由是可预期的**特殊读写形态**（海量 KV 读、倒排检索、高吞吐写），不是"潮流"。
- **纠偏**：绝大多数中小系统**一个关系型库就够**；NoSQL 通常是关系型的**补充层**（缓存 Redis / 搜索 ES / 日志 TSDB），**不是替代**。聊到缓存再引 Redis，聊到检索再引 ES，别一上来就摆两套存储。
- **背熟一句**：关系型卖"事务+关系"，NoSQL 卖"某种读写的极致"；先关系型打底，按痛点上 NoSQL 补位。
- **追问**：订单明细与库存为什么宁可放同一关系型库而不是拆成两个 NoSQL？——扣库存+写订单需要**跨行事务**，拆开后只能靠分布式事务/最终一致补偿，复杂度与风险高一个量级；先想清"这两个操作必须原子吗"再决定拆不拆。
- **再追问**：本项目一张 SQLite 就装下会话/消息/任务，还要不要 NoSQL？——不用，见第 26 题：写并发为 1、数据量小，Redis/MySQL 都暂无充分理由；将来要"多节点共享同一进度/加分布式锁"才考虑引 Redis。

### 2. 事务的 ACID 分别是什么？★

- **答（要点）**：
  - **原子性 Atomicity**：一组操作**全做或全不做**，中途失败整体回滚（undo 日志支撑）。
  - **一致性 Consistency**：事务前后数据满足**所有约束与业务规则**，从一种合法状态到另一种合法状态。
  - **隔离性 Isolation**：并发事务**互不可见中间态**（由隔离级别/锁/MVCC 提供）。
  - **持久性 Durability**：**提交即落盘**，断电/崩溃不丢（redo 日志支撑）。
- **背例子串讲**：转账"扣 A + 加 B"——中间失败要一起回滚（A）；两人合计不能凭空多钱（C）；转账中别人看不到"A 已扣、B 未加"的中间态（I）；提交后宕机钱也不丢（D）。
- **易错点**：C 常被误当成 DB 全包——其实**一致性主要是应用层责任**，DB 只能靠约束/触发器部分兜底；A 靠回滚日志、D 靠重做日志实现，这才是引擎的核心机制。
- **背熟一句**：A/D 是日志给的，I 是锁与 MVCC 给的，C 主要靠你的代码写得对。
- **追问**：Redis 事务（MULTI/EXEC）算 ACID 吗？——只保证命令"打包执行不被穿插"，**不保证出错原子回滚**（运行期错误不会撤销已执行的命令），持久化也看配置；缓存里的"事务"别当关系型事务用。

### 3. 隔离级别？脏读 / 不可重复读 / 幻读怎么区分？★

- **答（要点）**：四种隔离级别由低到高：
  - **读未提交**：能读到别人**未提交**的数据 → 连**脏读**都可能发生，生产基本不用。
  - **读已提交**：只读**已提交** → 防脏读，仍有不可重复读/幻读（PostgreSQL 默认）。
  - **可重复读**：同一事务内同一行多次读**值不变** → 防脏读+不可重复读；理论仍可幻读（MySQL InnoDB 默认，用**间隙锁**实际基本消掉幻读）。
  - **串行化**：并发事务互相串行 → 三类异常全防，并发能力最差。
- **三种读异常一句话记**：**脏读**=读到别人**未提交、随后回滚**的假数据；**不可重复读**=同一行两次读**值**不同（针对 **update**）；**幻读**=同一查询两次**行数/新增行**不同（针对 **insert**），多出来的行叫幻影行。
- **背熟一句**：级别往上，依次堵住脏读→不可重复读→幻读，代价是并发与锁开销上升。
- **追问**：隔离级别越严并发越差，为什么 MySQL 敢默认 RR？——RR 在 InnoDB 里由 **MVCC 快照读**实现，普通读**不加锁、不阻塞写**，所以"可重复读"不牺牲读并发；成本主要花在写范围时的间隙锁上。
- **再追问**：幻读为什么比不可重复读难防？——不可重复读锁"已存在的行"即可；幻读发生在**范围**上，要锁"还没插入的间隙"，会锁住本不该锁的范围、伤并发。所以多数业务停在可重复读，把"唯一约束/事务后重查"当兜底。

### 4. 锁：共享/排他锁，乐观/悲观锁？★

- **答（要点）**：按互斥度分**共享锁 S（读锁）**与**排他锁 X（写锁）**：**S-S 兼容，S-X 与 X-X 互斥**，即"读读可并行、读写与写写互等"。
- 按"冲突处理策略"分悲观/乐观两种风格：
  - **悲观锁**：假设必冲突，**先加锁再操作**，典型是事务内 `SELECT ... FOR UPDATE` 锁住行直到提交。适合**写冲突多**的场景（扣库存、领券、对账）；代价是并发下降、要小心死锁。
  - **乐观锁**：假设少冲突，**不加锁，更新时比对版本**：`UPDATE t SET name=?, version=version+1 WHERE id=? AND version=?`，**受影响行数 = 0 说明被别人先改了 → 回读重试**。适合**读多写少**；冲突比例高时重试反而更贵。
- **背熟一句**：悲观锁防患于未然，乐观锁亡羊补牢；选型看"冲突概率"与"加锁成本"。
- **追问**：`FOR UPDATE` 是不是只会锁一行？——它锁的是**扫描到的索引记录**；若 WHERE 条件**没走索引，会升级成锁全表**（或锁大量行），所以悲观锁条件必须命中索引——这也解释了为什么锁都是建在索引上的。

### 5. MVCC 是什么（概述）？★

- **答（要点）**：**多版本并发控制**：更新时不直接改旧行，而是**留下旧版本、新增一个版本**。InnoDB 用 **undo log** 保存旧版本，行内带隐藏列 `trx_id`（最近写入事务）、`roll_pointer`（指向旧版本）串成**版本链**。
- **普通 SELECT 是快照读**：按可见性规则挑一个"自己看得见的版本"来读，**不加锁、不阻塞写**；写才加行锁，且**不阻塞别人的快照读**。于是读与写互不阻塞，这是高并发读的关键。
- **可见性大意**（够背）：只能看见"事务开始前已提交"的版本；看不见未提交的，也看不见自己开始之后才提交的。对面试说清"读旧版本、不看脏数据"即可。
- **背熟一句**：MVCC 用"多版本 + 快照读"换"读写互不阻塞"，把读从锁里解放出来。
- **追问**：MVCC 能完全替代行锁吗？——不能。它解决**读读/读写**的并发；**两个写仍然要行锁串行**；`SELECT ... FOR UPDATE` 这类**当前读**必须加锁去读最新版本。

### 6. 唯一约束/唯一索引做防重复（幂等）？★

- **答（要点）**：给"**业务幂等键**"建 **UNIQUE 唯一索引**，让数据库当**最终防线**：并发两笔相同请求同时插入，只有一笔成功，另一笔撞唯一冲突抛错（Python 里是 `sqlite3.IntegrityError`）→ **捕获后按"已存在"处理**，从而做到防重复/幂等。
- **为什么不能只靠"先查后插"**：查与插之间存在**时间窗**，两个请求同时穿过窗口就会都插进去——"先查"只是省事的**快路径**，"唯一索引兜底"才是**正确性保证**，二者配合是标准答案。
- **幂等键怎么选**：选请求里**稳定、可归一化**的东西（订单号、支付回调号、参数指纹），而不是自增 id——自增每行都不同，起不到"同请求去重"的作用。工程常见形态：`业务号/参数指纹 + UNIQUE + 状态列` 的请求账本表。
- **背熟一句**：先查是优化，唯一键才是防重的根；多补一句"业务键不进主键、另加 UNIQUE"更显功底。
- **追问**：唯一键和主键什么关系？——主键是**最核心的唯一索引**（通常还兼聚集/定位行）；唯一索引可以建多个，用来约束普通业务列；注意唯一索引列**允许一个 NULL**，多个 NULL 之间不判重。
- **再追问**：幂等键常配一个"状态列"，怎么配合？——同一键允许重放，但状态机判断：已完成直接返回结果、进行中查进度、终态失败才允许重试，从而不产生第二次副作用；第 24 题 sr_tasks 正是"唯一指纹 + 状态"这套。

## 二、索引与表设计

### 7. 索引原理：为什么是 B+ 树？★

- **答（要点）**：数据库最贵的是**磁盘 IO**，索引的目标是**用最少的磁盘页访问定位数据**。B+ 树是**多叉平衡树**，三个关键设计：
  - **非叶子节点只存 key**：一页能塞极多 key → **扇出大、树矮**：百万~亿级数据树高也只有 **3~4 层**，一次查询 ≈ 树高次磁盘 IO。
  - **叶子节点存数据（或主键）**且**按 key 有序串成链表** → 天然支持**范围查询、排序、顺序扫描**；相邻 key 常落在同一磁盘页，**预读友好**。
- **对比记忆**：红黑树/二叉搜索树高约 log₂N，百万级要 ~20 层即 ~20 次随机 IO，节点在磁盘上也不连续；哈希索引**只能等值（`=`）**，做不了范围/前缀/排序，只能当辅助。B+ 树是"等值 + 范围"都高效的选择。
- **背熟一句**：B+ 树用"矮 + 有序 + 顺序 IO"换低延迟；矮靠非叶子只存 key，有序靠叶子链表。
- **追问**：为什么非叶子只存 key 不存数据？——一页能放更多 key → 扇出更大 → 树更矮 → 查询 IO 更少；且数据只在叶子，**所有查询路径长度一致、稳定**。

### 8. 聚集索引 vs 非聚集索引？★

- **答（要点）**：
  - **聚集索引（聚簇索引）**：叶子节点**直接存整行数据**，表数据物理排列大致随索引序，**一张表只能有一个**（InnoDB 主键即聚集索引；没主键就找唯一非空列，再没有用隐藏 rowid）。
  - **非聚集索引（二级索引）**：叶子存**主键值**（InnoDB 是聚簇主键值），先按二级索引找到主键，再去聚集索引取整行 = **回表**。
- **工程推论**：① 主键**最好有序自增**——随机主键让新行插到叶子中间，引发**页分裂、碎片、缓存命中差**；② 让查询列都落进索引 → **覆盖索引**免回表，`SELECT *` 最容易破坏覆盖；③ 每个二级索引都"隐式携带主键"，所以**主键别用超长字符串**，否则所有二级索引都变胖。
- **背熟一句**：聚簇=整行在索引里、只能一个、物理近主键序；二级=先找主键再回表；覆盖索引就是"不回表"。
- **追问**：`SELECT name FROM t WHERE name LIKE '张%'`，建了 `(name)` 索引还回表吗？——只查 name 且 name 已在索引 → **覆盖查询不回表**，`EXPLAIN` 的 `Extra` 会显示 `Using index`。
- **再追问**：覆盖索引有代价吗？——有：冗余列占索引空间，更新这些列要同步改索引；所以只为高频查询加需要的列，别图省事把整行塞进联合索引。

### 9. 主键怎么选？★

- **答（要点）**：推荐**无业务含义、单调递增的代理键**：自增 bigint、雪花 ID、有序 UUID（UUIDv7）等。
- **为什么**：InnoDB **按主键聚簇**，原生随机 UUID 每次插入都落到叶子**中间** → 页分裂、磁盘碎片、缓存命中差；自增/UUIDv7 是**尾部追加**，顺序写友好。长字符串主键还会被复制进每个二级索引，让索引膨胀。
- **业务上可唯一标识的字段**（手机号/身份证/订单号）：**另建 UNIQUE 约束当业务键**，别直接当主键——它们**可能变更**（改主键 = 改聚簇位置，代价大）、**可能很长**、把业务语义焊进了物理布局。
- **兜底回答**：若团队倾向 UUID，选**有序 UUID（UUIDv7）或雪花**；面试重点是讲清"随机无序 vs 单调"对聚簇表的影响，而不是背一种方案。
- **背熟一句**：主键只管"稳定唯一有序"，业务键用 UNIQUE 表达；考点在"无序主键怎么伤聚簇表"。
- **追问**：分库分表后全局主键怎么生成？——雪花算法（时间戳+机器位+自增序列）或独立发号器/号段服务；答出"**趋势递增、全局不撞、可解析时间**"即算完整。

### 10. 索引为什么会失效？explain 怎么看？★

- **答（要点）**：常见失效场景：
  1. 索引列上**做函数/运算**：`WHERE YEAR(created)=2024`、`WHERE id+1=5`（索引里存的是**原始列值**）。
  2. **隐式类型转换**：字符串列查数字、索引列参与类型不一致的比较。
  3. 前导模糊 `LIKE '%xx'` 走不了索引（`'xx%'` 可以，`'%x%'` 中段匹配也走不了）。
  4. 联合索引**不满足最左前缀**：`(a,b)` 上只查 `b`、不查 `a`。
  5. `OR` 连接的另一个条件**无索引**，导致整体变全表。
  6. 优化器判断**全表更快**：表太小、列区分度太低（如性别）。
  另：`NOT IN / != / IS NOT NULL` 常无法用索引（依版本与统计）。
- **explain 看四列（背关键）**：`type` 从 `ALL→index→range→ref→eq_ref→const` **越右越优**，看到 `ALL` 警惕；`key` 显示实际用的索引（空=没走）；`rows` 预估扫行数；`Extra` 里 `Using index`=覆盖索引（好）、`Using filesort`=排序没走索引、`Using temporary`=产生临时表（通常要优化）。
- **背熟一句**：失效四兄弟——函数包裹、类型转换、前导 `%`、丢了最左；EXPLAIN 只看 type/key/rows/Extra 四列。
- **追问**：`(a,b)` 联合索引，`WHERE b=1 AND a=2` 走吗？——**走**，优化器会重排等值条件顺序，关键是**必须包含 a**；但 `WHERE b=1`（不含 a）就不走。设计口诀：等值列在前、范围列放后、ORDER BY 字段尽量收进索引。

### 11. SQL 基础：JOIN 有哪几种？什么时候用？★

- **答（要点）**：
  - **INNER JOIN**：只留两表**匹配**的行（内连接）。
  - **LEFT / RIGHT JOIN**：保留左/右表**全部行**，另一边无匹配补 NULL。
  - **FULL OUTER JOIN**：两表都保留（MySQL 原生没有，用 `LEFT ... UNION RIGHT` 模拟）。
  - **CROSS JOIN**：笛卡尔积（无连接条件、数据翻倍，慎用）。
- **工程要点**：① JOIN **关联列必须建索引**，否则左表每行都去右表全扫（N+1 次扫描）；② **先缩小再连接**：先 WHERE 过滤或用子查询把驱动表变小；③ 多张大表 JOIN 要防临时表过大/内存溢出；④ `LEFT JOIN` 后若把**只对右表成立的过滤**放 `WHERE`，会把补出的 NULL 行滤掉、效果变成内连接——这是隐蔽 bug，应放 `ON`。
- **背熟一句**：INNER 只留交集，LEFT 保左丢右补 NULL；过滤放 ON 还是 WHERE 决定了会不会偷变 INNER。
- **追问**：`LEFT JOIN` 时右表有多行匹配会怎样？——**结果行数放大**（一对多产生重复左表行）；应保证关联列唯一，或用 `DISTINCT`/聚合去重——这是"Join 前先想清基数"的考点。

### 12. 范式与反范式？★

- **答（要点）**：范式用于**消除冗余、保证写一致性**：**1NF** 列原子不可再分；**2NF** 消除对**复合主键的部分**依赖；**3NF** 消除**传递依赖**（非主属性不依赖其它非主属性）；BCNF 更严格。业务开发通常到 3NF 即可。
- **反范式**：为**读性能刻意冗余**——订单表直接冗余**商品名/单价快照**、热点表加冗余计数、宽表省 Join、预聚合表省实时统计。代价是**写时要多处同改、一致性要自己维护**，可能漂移。
- **取舍本质**：范式让"写省心、读要 Join"，反范式让"读省心、写要自己保一致"。这是**读模型与写模型**的权衡，不是对错问题。
- **背熟一句**：范式治冗余的病，反范式治 Join 的慢；订单存快照是反范式最经典的正解。
- **追问**：电商下单后商品改名了，历史订单变不变？——一般**不变**：订单应存下单时快照，可独立展示、不依赖商品表后续改动；这正是"用可控冗余换读的稳定与简单"。
- **再追问**：反范式最容易踩的坑？——多处冗余同义数据、更新漏一处就"不一致"；所以凡冗余先问"这里允许读旧一点吗"，再配兜底（对账脚本/定时校正/短 TTL 强制重建）。

### 13. 连接池是什么思想？★

- **答（要点）**：数据库**建连成本高**（TCP 握手 + 鉴权 + 服务端为每连接分内存/线程资源）。若每请求都新建/关闭连接，QPS 一高就成"建连风暴"。**连接池**：预先建好一批连接复用，**用完归还不真关**；池负责上限控制与失效回收。关键参数：初始/最大连接数、空闲超时、获取超时。
- **为什么上限不是越大越好**：连接数超过 DB `max_connections` 或它能同时服务的上限，多余的只会**排队等资源甚至被拒**；池大小要和 DB 能力、应用并发模型匹配（压测得来），"越大越猛"是误区。
- **Python/FastAPI 注意**：DB-API 连接**不可跨线程共享**——并发要"每线程一条 / 池按线程分配"，而不是共享同一连接；请求结束是**归还**而不是关闭。Web 框架的线程池与 DB 连接池是两回事。
- **背熟一句**：连接池 = 复用 + 限额；它扛得住"反复建连"的浪费，扛不住"DB 本身打满"。
- **追问**：连接池和线程池是一回事吗？——思想相同（复用对象 + 上限控制），但复用对象不同：一个复用**连接**、一个复用**执行线程**；两者常配合出现。

### 14. 分页 / 大数据量分页优化？★

- **答（要点）**：朴素 `LIMIT offset, n` 的痛点是：**offset 越大，引擎仍要先扫并丢弃前面 offset 行**（`LIMIT 1000000, 20` 要扫 100 万行再丢），这叫**深翻页**。方案：
  - **游标/keyset（翻页法）**：`WHERE id > 上次返回的最大 id ORDER BY id LIMIT 20`——**用索引直接跳到该走的位置**，恒定快；代价是**不能任意跳页**、翻页途中新增行会漏（适合信息流"下一页"）。
  - **排序走索引**：`ORDER BY` 字段进索引，避免 `Using filesort`。
  - **别 `SELECT *`**：只取需要的列减少 IO；大字段（BLOB/长文本）按需单独查。
- **背熟一句**：深翻页慢在"先扫后丢"；用游标键"带上次位置走索引"就绕开了 offset。
- **追问**：导出一百万行也很慢，跟分页没关系？——导出本质是**扫全表 + 排序**，瓶颈不在 `LIMIT`；此时按 id 分段（每批 5 万条）顺序批量读更稳，还能降低单次内存峰值。

## 三、SQLite 与消息

### 15. SQLite 特点：嵌入式 / 单文件 / 锁粒度？何时够用，何时换 MySQL/PostgreSQL？★

- **答（要点）**：
  - **嵌入式**：**没有独立服务进程**，库以文件形式被应用直接调用；Python 的 `sqlite3` 是**标准库、零安装**。
  - **单文件**：一个 `.db` 文件 = 整个数据库，**拷文件即备份/迁移**，部署运维成本极低。
  - **Serverless / 零配置**：不开端口、无账号体系；但标准 SQL、事务、索引、视图一应俱全。
  - **锁模型**：写锁是**库级（整库文件）**而非行级——通常**同一时刻只允许一个写者**；配 WAL + `busy_timeout` 后可读不阻塞写、多个写者排队。**写并发上限低**是它最大的边界。
- **何时够用**：**单进程 / 低写并发 + 单机部署 + 想零运维**——本地工具、Agent 内部状态、小服务、配置与账本、原型，数据量到 GB 级也常见够用。判断标准不是"能存多大"，而是"**写并发和部署形态**"。
- **何时换 MySQL/PostgreSQL**：多进程/多机**高并发写**、要网络端口让多客户端连、要**行级并发控制**、要账号权限/主从复制/高可用/监控体系、单文件装不下的量级。PG 开发者体验更好（JSON/窗口函数/约束严格），MySQL 运维生态更普及——能说出这条差别就够。
- **背熟一句**：SQLite 输在"写并发上限"，不是"正确性"；够不够用先问"有几个并发写者"。
- **追问**：SQLite 安全吗？为什么能当事务库用？——事务能力完备；库级写锁在**单写者**场景反而天然规避了大多数死锁与隔离边界问题。但要显式管好事务：Python `sqlite3` 在手动 commit 前是"隐式开着一个事务"，别以为每条 SQL 都已持久化，读多写多时要 `BEGIN...COMMIT` 成组提交。

### 16. ORM vs 手写 SQL？本项目为何用裸 sqlite3？★

- **答（要点）**：ORM 优点：**对象映射省样板、参数化天然防注入、迁移/模型可管理、可读性好、换库成本低**。ORM 缺点：**N+1 查询**（循环里逐条查库）、复杂 SQL 表达费力、生成的 SQL 是黑盒、事务与锁的时机被遮住。
- 手写 SQL 优点：**精确可控、性能可预期、事务边界看得清**；缺点：样板代码多、要自己记着参数化防注入。
- **适用判断**：表多、模型复杂、要快速 CRUD、团队熟 ORM → 用 ORM；**表少、SQL 简单、对延迟/事务时机敏感、强调零依赖** → 裸 SQL 反而更干净。
- **本项目取舍**：`store.py` 用**裸 `sqlite3` + 参数化 SQL**——只有三张简单表（sessions/messages/sr_tasks），SQL 直白可控；**无框架依赖、依赖少、离线可控**（与全仓库"本地 vendor、可离线自测"的约束一致）；每条消息追加是**显式事务**，方便把"落库时机（回合前 checkpoint）"这类正确性细节讲清楚——ORM 恰恰会把这个时机藏起来。
- **背熟一句**：ORM 用抽象换效率；表少而 SQL 直白时，裸 SQL 的"看得见"就是最大价值。
- **追问**：裸 SQL 怎么防注入？——一律 `?` 占位符参数化（`execute(sql, (…))`），**绝不字符串拼接用户输入**；本项目所有取值入参都走占位符，SQL 语句本身是常量。
- **再追问**：什么信号出现就该把"裸 SQLite"升级成 ORM/正经 DB？——出现跨进程并发写、消息要按多字段检索、表结构频繁变更、多端要连同一个库时；SQL 已全部收口在 `store.py`，届时只改这一个模块即可（第 26 题）。

### 17. 消息队列什么时候才需要？★

- **答（要点）**：MQ 解决"**生产快、消费慢、要解耦**"三类问题：
  - **削峰填谷**：突发流量先进队列，消费者按能力消化，**保护 DB/下游**不被瞬时峰值打垮。
  - **异步解耦**：下单后发短信/更新搜索/通知**不阻塞主流程**；生产者不关心谁消费、消费者挂了也不影响下单。
  - **可靠投递/重试/死信/背压、事件广播（fan-out）**。
- **别为了"高级感"上 MQ**：单机低频、无强顺序/送达需求时，MQ 引入的是**新故障面**——消息到底发没发成功、重复消费、丢消息、多一个要运维的组件。此时**一张任务表 + 状态机**更简单可靠。
- **本仓库**：GPU 超分提交走 **SQLite 任务表 + Slurm 队列**而不是 MQ：Slurm 本身就是成熟 GPU **作业队列**（`sbatch` 排队/调度、健康检查闸门、GPU 数量不对就停），SQLite 只记任务元数据（fingerprint/job_id/status/参数），代码轮询 `squeue/sacct` 收结果；架构决策表里写得明白——"SQLite 记任务元数据，**Redis 以后需要再加**"。若将来真要事件化，再让 MQ 承载"任务完成/开始"这类事件，**先有明确需求再引组件**。
- **背熟一句**：MQ 治"峰值、解耦、广播"；任务表 + 状态机能覆盖大半异步场景且零新增运维。
- **追问**：任务表方案的重试怎么做？——重试 = 查状态机决定"复用已有结果还是重提任务"，见第 24 题 sr_tasks 的实现；这正是"不引 MQ 也能拿到可靠语义"的实例。

## 四、Redis 与缓存

### 18. Redis 是什么？为什么快？★

- **答（要点）**：Redis = 基于内存的**键值（NoSQL）存储**，常用作缓存/计数器/会话/排行榜/简单队列/分布式锁。**为什么快**，按层次答：
  - **数据在内存**：无磁盘随机读，内存与磁盘的带宽差一个数量级。
  - **单线程执行命令**（6.0+ 只把网络读写拆给多线程，**命令执行仍单线程**）→ **无锁、无竞态、天然原子**，省掉锁竞争与上下文切换。
  - **IO 多路复用（epoll）**：单线程同时盯**成千上万连接**，网络等待不占命令执行时间——瓶颈是网络而非 CPU。
  - **数据结构 + 命令精简**：操作都很短、C 实现，无解释执行开销。
- **背熟一句**：快 = 内存 + 单线程免锁 + 多路复用扛连接；单线程换来原子与简单，多核靠多实例横向补。
- **追问**：单线程岂不是浪费多核？——命令执行本身远占不满 CPU，瓶颈通常在网络/内存；单线程的代价换来了**实现简单与命令天然原子**，要多吃核就开多实例/集群，这是官方扩展路径。

### 19. Redis 数据结构与经典场景？★

- **答（要点）**：
  - **String**：缓存任意值、`INCR` 计数器（库存/验证码/限流）、session；`SETNX` 是分布式锁的原料。
  - **Hash**：一个**对象的多个字段**（用户资料、购物车、配置），`HGETALL/HINCRBY` 改单字段不用整对象序列化往返。
  - **List**：`LPUSH + BRPOP` 作**简单消息队列**（阻塞取）、最新动态/时间线（`LRANGE` 取最近 N 条）。
  - **Set**：**去重**、`SISMEMBER` 判会员、`SINTER/SUNION` 共同关注/推荐、抽奖/签到（无序集合）。
  - **ZSet（有序集合）**：按 score 排序且去重——**排行榜**、**延迟队列**（score=到期时间戳，`ZRANGEBYSCORE` 取到期项）、滑动窗口限流。
  - 延伸：Bitmap（签到/在线位图）、HyperLogLog（亿级 UV 去重计数）、Geo（附近的人）。
- **选型记忆**：**数据形状 × 访问方式**——单字符串用 String、对象多字段用 Hash、去重/判断用 Set、要排序取 TopN 用 ZSet、FIFO 阻塞消费用 List。
- **背熟一句**：String 是本体，Hash 管对象，List 排队，Set 判重，ZSet 排序，各管一摊别乱套。
- **追问**：排行榜同分怎么排？——ZSet 同 score 按 member 字典序（对数字/中文不直观），工程上把 score 编码成"分数×大常数 + 时间倒序位"，让**先到者排前**（分数优先、时间次之）。

### 20. 缓存穿透 / 击穿 / 雪崩与对策？★★

- **答（要点）**：三者共同点是"**缓存没挡住 → DB 被打**"，但对象与对策不同：
  - **穿透**：查的 key **根本不存在**，缓存永远 miss，无效/恶意请求直打 DB。对策：**空值也缓存（短 TTL）**、**布隆过滤器**前置（集合里没有必不存在）、入参合法性校验。
  - **击穿**：**单个热点 key 恰在过期瞬间**失效，海量并发同时回源。对策：回源**加互斥锁**只放一个线程查 DB、热点**逻辑永不过期 + 后台异步刷新**、热点预热。
  - **雪崩**：**一大批 key 同时过期**或 Redis 整体宕机，DB 被瞬时洪峰打垮。对策：过期时间加**随机 jitter** 错峰、**多级缓存**（进程内本地缓存兜 Redis 空档）、**熔断/限流/降级**、Redis 高可用（哨兵/集群）。
- **区别速记表**（本系列唯一表格）：

| 异常 | 打击对象 | 直接原因 | 首选对策 |
|---|---|---|---|
| 穿透 | 不存在的 key | 查询永远 miss | 空值缓存 / 布隆过滤器 |
| 击穿 | 单个热点 key | 过期瞬间并发回源 | 回源互斥锁 / 逻辑永不过期 |
| 雪崩 | 一批 key 或整个 Redis | 同时过期 / 宕机 | 过期随机化 / 多级缓存 / 高可用 |

- **背熟一句**：穿透是"查不到"，击穿是"一个热点刚过期"，雪崩是"一批/整个一起没"；对策对着原因打。
- **追问**：互斥锁回源拿到结果后要不要立刻写缓存？——要，且只在"**未命中并抢到锁**"的线程里回源+写缓存（带 TTL），其它线程**自旋等缓存就绪**再读；不回填的话下一个请求照样击穿。

### 21. 缓存与 DB 的一致性（先删后更 / 延迟双删）？★

- **答（要点）**：主流是 **Cache-Aside**：读 → 未命中查 DB → 写缓存；**写 → 先更新 DB，再删除缓存**（先更后删）。**为什么删而不更新**：并发写时"更新缓存"极易把旧值或乱序写回；"删除缓存"让缓存永远只承载"最近一次 DB 成功后的读"，正确又简单。
- **"先删后更"的老写法**（先删缓存再写 DB）有窗口：删完缓存、DB 还没写完时，另一个请求会把 DB **旧值**回填进缓存 → 缓存长期脏。缓解是**延迟双删 Double Delete**：删缓存 → 写 DB → **延迟约一个读往返时间（几百 ms~1s）再删一次**，把可能回填的旧值清掉。
- **本质**：DB 与缓存**无法放进同一个事务**（跨存储），所以给的是"**最终一致 + 可接受的短窗口**"。兜底：**TTL**（最坏脏到过期自然消失）、删缓存失败走 **MQ / 订阅 binlog（如 Canal）异步重删**。
- **背熟一句**：写路径 = 先更 DB 后删缓存；老式先删后更靠"延迟双删"补窗口；跨存储没有原子，只能收敛窗口 + TTL 兜底。
- **追问**：为什么"先更后删"优于"先删后更"？——先删后更在"删后、写前"有较长空窗，命中率骤降且易被旧值回填；先更后删的窗口只有"DB 更新后、删缓存完成前"一瞬间，且删的是已过期的旧缓存——**窗口短、风险小、命中率高**，所以主流选它。
- **再追问**：TTL 设多长才安全？——以"业务能容忍的脏窗口"为上限：宁可设短让缓存频繁重建，也别设长让脏数据长时间可见；因为删缓存失败只能靠 TTL 兜底，TTL 是最后一道闸。

### 22. Redis 持久化：RDB / AOF？★

- **答（要点）**：Redis 是内存库，持久化决定**重启后还剩多少数据**：
  - **RDB**：`fork` 子进程**定期全量快照**落盘（dump.rdb）。优：文件紧凑、**恢复快**、适合定期备份；缺：**两次快照之间丢数据**、fork 大实例瞬时阻塞（写时复制会短暂占内存）。
  - **AOF**：把**每条写命令**追加到日志。刷盘策略：`always`（每条 fsync，最稳最慢）、`everysec`（默认，最多丢 1 秒）、`no`（交给系统）。缺：文件大、恢复要重放，靠 **AOF rewrite（bgrewriteaof）** 压缩；优：**丢得少**。
  - **4.0+ 混合持久化**：AOF rewrite 时用 RDB 快照打底 + 之后的增量命令，兼顾"**恢复快**"与"**丢得少**"。
- **选型**：当缓存可不开持久化；能容忍丢秒级数据选 AOF everysec；要快速重启、能接受周期性丢失选 RDB；**两者都开**最稳（常用配置）。
- **背熟一句**：RDB 是定期快照（快但丢得多），AOF 是命令日志（丢得少但文件大），混合模式折中，重启先加载 AOF。
- **追问**：AOF 和 RDB 都开启，重启加载哪个？——**AOF**（数据更全）；AOF 损坏/缺失才退回 RDB。所以别以为"开着 RDB 就一定能恢复最新状态"。

### 23. 分布式锁的朴素实现与问题？★

- **答（要点）**：单实例 Redis 加锁经典是 **`SET key value NX EX 秒` 一条原子命令**（错误示范：`SETNX` 成功后再单独 `EXPIRE`——若中间崩溃会留下**永不释放的锁**）。解锁**必须带 token**：value 放唯一随机串，删除前用 **Lua `if GET==myToken then DEL`** 校验所有权，防止误删"别人后来接手的锁"。
- **朴素实现的问题**：① **锁过期但任务没跑完** → 锁自动释放、别人拿到 → 同一资源被并发执行（需**看门狗续期**）；② **主从切换**瞬间锁记录还没复制到新主就丢了 → 别人也能拿锁；业界 Redlock 试图解决，但**仍有争议**（依赖时钟与网络分区假设）。
- **工程现实**：分布式锁**只挡并发尖峰，不保证逻辑正确**——铁律是"**锁 + 业务幂等键双保险**"：就算锁失守，重复执行也会被业务唯一键/状态机拒掉。本项目即此思路：**没引 Redis 锁**，用 sr_tasks 唯一指纹 + 状态机保证外部副作用只发生一次（见第 24 题）。
- **背熟一句**：加锁要"NX EX"一条命令，解锁要带 token 用 Lua；锁会过期会丢，正确性靠业务幂等兜底。
- **追问**：锁都失守了，双保险怎么收场？——重复执行要么**结果幂等**（重复提交同一 GPU 作业毫无意义），要么撞 **UNIQUE/状态校验**被拒；答出"分布式锁不解决正确性、业务必须容忍重复执行"是最大区分度。
- **再追问**：如果一定要用 Redis 锁，怎么把风险压到最低？——加锁统一走"NX EX"单命令、value 放随机 token、解锁用 Lua 校验再删、任务内看门狗续期；同时业务侧保留幂等键，明确"锁可能失守、靠业务兜底"。

## 五、仓库实践注记（把八股讲成项目）

### 24. sr_tasks 用"参数指纹 + 先查后提交 + 先记意图再执行副作用"防重复提交？★★

- **答（要点）**：GPU 超分提交是**外部副作用**（`sbatch` 会真去排 GPU 跑几小时），重复提交代价极高，[run_sr.py](backend/services/run_sr.py) 里做三层防重：
  - **参数指纹**：`task_fingerprint` 把参数 `json.dumps(sort_keys=True)` 规范化后做 **SHA-256**，相同参数必撞同一指纹；[store.py](backend/services/store.py) 中 `sr_tasks.fingerprint` 建了 **UNIQUE 唯一索引**，数据库层保证同指纹**只能有一行**——这就是第 6 题"唯一索引做幂等"的落地。
  - **先查后提交**：`submit_run_sr` **在任何副作用之前**先 `get_sr_task(fp)`：若已有 job_id，就 `squeue/sacct` 查调度器——**active / COMPLETED 直接复用返回、绝不重提**；只有 FAILED/失联等终态才允许重提（`_resolve_existing`）。代码注释点明这是 **deepseek-harness repair.ts 语义："别假设副作用没发生"**。
  - **checkpoint before side effect（先记意图、再执行副作用）**：写好 config.xml/batch 脚本后、`sbatch` 前先 `put_sr_task(status="new", job_id=None)` 提交落库，sbatch 成功后再 `update_sr_task_job(fp, job_id)` 补记。若两次写之间崩溃，留下的是 **job_id=None 的"意图行"**：恢复时 `_resolve_existing` **直接抛错"上次提交被中断、结果未知，去查 squeue，不要盲目重提"**——宁可让用户确认，也绝不重复提交 GPU 任务。
- **背熟一句**：指纹做键、先查决定复用还是重提、意图先落库再碰外部世界——把"外部副作用"框进了可审计的状态机。
- **追问**：为什么不能把"落库 + sbatch"包进一个 `BEGIN...COMMIT` 事务？——sbatch 是**外部系统调用**，本地 SQLite 事务**管不到外部**；所以"先写意图 → 执行外部动作 → 再补记结果"才是跨系统一致性的实现手段，失败恢复靠**状态机判断**而不是靠回滚。

### 25. 消息按"回合前落库"，崩溃后如何恢复？★

- **答（要点）**：[store.py](backend/services/store.py) 把 `messages` 表设计成**只追加（append-only）的 wire-format 消息日志**——存的就是 OpenAI 兼容消息 JSON，**不是框架状态**。每次 `append_message` 在一个事务里完成插入并提交，**返回即已持久化**。
- **关键时机 = 回合前 / 每次要调工具之前落库**（deepseek-harness 的"checkpoint before side effect"）：助手要执行工具时，**先把该回合记录写进 DB，再真正调工具**。这样中途崩溃最多留下一个标记"未完成"的可修复回合，**绝不会出现"工具已执行、但数据库没记录"** 的悬空副作用。
- **恢复语义**：`resume=True` 续接时**按 messages 日志原样重建对话**（`get_messages` 依 seq 顺序回放 JSON）；对"上次结果未知"的回合，生成"**上次结果未知、不要盲目重试**"的提示交给用户/Agent 决定，**不自动重放工具**。
- **背熟一句**：消息是只追加的 checkpoint，先落库再动手；崩溃后最多多一个"未完成回合"，绝不出现"干了没记账"。
- **追问**：消息存 JSON 而不拆列，查单字段不方便，值不值？——值。它保证与 OpenAI 兼容契约**零转换原样一致**、恢复逻辑最简单（顺序回放即可）；"按字段检索历史消息"不是该场景的高频需求——**表结构向访问模式妥协**，正是反范式取舍在实践里的体现。

### 26. 为什么选 SQLite 单库放 sessions / messages / sr_tasks 三张表？★

- **答（要点）**：决策背景见 [platform-tutorial.md](docs/knowledge/platform-tutorial.md) 附录 A 的架构决策表。四点理由：
  - **并发形态匹配**：Agent 主循环是**单进程顺序驱动**，写是低频串行（回合前落一条消息、提交时写一条任务行），恰在 SQLite"单写者 + 整库锁"的**舒适区**——写并发不是瓶颈，**根本用不上行级锁/重型 DB**。
  - **嵌入式单文件**：这三张表是"会话元数据 + 消息日志 + 任务账本"，量级远小于图片等资产，**一个 `.db` 文件随项目走、拷走即备份**，零运维零端口。
  - **关系简单、访问模式单一**：消息按 session_id 顺序回放、任务按 fingerprint 幂等查询，都是**单表顺序/按键访问**，没有复杂 Join 或跨表事务——**没有引入 MySQL/Redis 的充分理由**。
  - **契合总约束**：仓库强调"**依赖少、离线可控**"，`sqlite3` 是标准库、store 无框架依赖（源码注释写明 *No framework deps*）；架构决策表对 Redis 的定位是"**以后需要再加**"（多会话/多节点共享、分布式锁、消息队列时），当前单机单循环用不上。
- **背熟一句**：先问"并发形态配不配得上"再选库——单进程低频写配 SQLite 是恰到好处，不是偷懒。
- **追问**：将来三张表会不会难迁移？——Store 类把**全部 SQL 收口在 `store.py` 一个模块**、schema 又极简，将来要换库**只改这一个文件**；这是"**接口隔离 + 极简 schema** 换迁移余量"，也符合"先把正确性做对、别过度设计"的演进路径。
