# 稀疏条带本地预览读取优化

日期：2026-11-09。代码与合成测试通过；真实 X 盘大图耗时待核。

## 原因与改动

旧 `sparseSample` 每个采样行单独执行一次 `Source.read`，每 8 行等待整组完成。网络盘的小请求和慢请求会放大等待；像素循环还反复计算采样列并调用 DataView。`decodeGeoTiff → sparseDecode` 重复解析条带头，各读取最多 2 MiB。

- 按文件偏移排序采样行，合并附近的读取；输出仍按原目标行写回，支持乱序条带偏移。
- 合并请求最多 1 MiB，间隙最多 64 KiB，读取跨度不超过有效采样行字节和的 1.5 倍。相距较远的采样行不合并，避免退化为全文件读取。
- 最多 8 个读取持续补位，不再等待每组最慢请求。按最大请求大小将并发读取缓冲约束在 8 MiB；单行超过此预算时仍允许单请求读取，预览输出数组另按既有内存规则分配。
- 采样列只计算一次；原生字节序且地址对齐时用类型数组，其他情况继续用 DataView。修复大端 float32 被固定按小端读取的问题。
- 复用已解析的条带布局，省掉一次重复头部读取。读取异常停止派发后续任务；已派发读取结束后不再写入结果。截断采样行明确报错。

## 兼容性与验证

不改变预览分辨率、端点对齐的最近邻坐标、自然值输出、拉伸、导出及原有解码分派。仍只加速既有无压缩单波段稀疏路径；压缩、多波段等继续走原有 UTIF/geotiff 链路。`stripsTouched` 延续原有采样行计数口径，`bytesRead` 记录实际返回的读取字节数。

`sparseRead.test.ts` 验证合并、读取范围、并发补位、进度、乱序/非对齐布局、大小端、8/16/32 位整数、float32（含 NaN/Infinity）和截断数据。既有 `tifDecode.test.ts` 覆盖 Classic/BigTIFF、稀疏/分块像素 golden，新增编排测试断言只读一次头部。

命令（frontend 目录）：

```text
npx vitest run src/lib/__tests__/sparseRead.test.ts src/lib/__tests__/tifDecode.test.ts src/lib/__tests__/source.test.ts
npm run typecheck
npm run build
```

专项 60 项通过，类型检查及构建通过。1024×1024 uint16 连续行合成用例：数据读取从旧机制的 1024 次降至 2 次，总读取字节数不变。此为请求数量验证，不代表真实网络耗时提升 512 倍。宽行、大采样间隔等无法合并的布局主要受益于补位并发与像素循环优化。

## 部署与边界

更新前端 `frontend/dist` 并刷新页面。本轮不解决 X 盘拖入时系统/浏览器禁止光标；服务端 W/X 路径归一的部署说明见 `docs/status/config_locations.md`。优先恢复服务端 JPG 预览链路，通常比浏览器经网络盘抽读更适合大图。

现场用同一图、同一预览档位分别记录冷/热缓存耗时、卡片实际预览尺寸与读取字节数。真实盘阵不可从开发机访问，未承诺固定秒数或所有布局同等加速。
