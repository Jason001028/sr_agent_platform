# 磁吸预览倍率控件（2026-10-30）

2026-10-31：排查 1:1 档位 `could not be decoded`：`decodeJpgToCanvas`
原先在 `createImageBitmap(blob)` 全尺寸解码完成后才缩到 4096，原尺寸 JPG
存在解码峰值内存风险。现在 `lib/jpegBitmap.ts` 仅读 JPEG 段头取得 SOF 尺寸，
在解码请求中传入长边 4096 的 resize 参数（2026-11-10 起统一到 16384，见下），
之后仍保留画布尺寸保护及 bitmap.close。
失败信息附源 JPG 尺寸及低档位重试提示，不自动重试全尺寸解码。
1:1 仍表示服务端采样档位。2026-11-10 统一口径：前端显示层、服务端生成、
本地解码与整幅 JPG 准入的长边上限都改为 16384（4096×4，与 Chromium 画布
16384² 面积上限同口径）；长边不超过 16384 的档位按真实采样交付，超过才截断。
因此不再出现「1:1、1/2、1/4……都缩成 4096」的档位合并。本地 TIFF 解码仍保留
256MB Float32 预算，大图可能比 16384 更早封顶 —— 那是有据可查的内存保护，状态栏
报实际长边与比例。

同一日把上限做成平台级设置：`设置 → 真分辨率长边` 提供 4096 / 8192 / 16384，
默认 16384；值存服务端 SQLite（`platform_settings` 表，`GET/PUT /api/settings`），
所有机器共用，不是 localStorage。前端启动/窗口回焦/打开设置面板时同步；改完后
当前可见影像按新上限重载。服务端规则戳追加 `;max=N`，旧戳（没有 `;max=`）与
不同上限的产物一律判废：调低能立即释放内存，调高也不会继续命中旧的 8192 缓存。
设置只影响**预览/显示**上限，本地 JPG 导出仍固定长边 4096。

三档不提供 16383：它与 16384 只差 1 像素，画布面积几乎相同，却会让状态栏出现
一个奇怪的分母，也不会换来更安全的余量；要省内存就选 8192。

16384 档位的峰值内存
仍可能很高（画布 + Float32 + 解码位图），JPG 像素改为逐块读 RGBA 以去掉整图副本；
真实内网图仍需确认。若仍失败，应考虑服务端切片，不能把 resize 当作任意大图的保证。
针对性回归 16 项通过（含 baseline/progressive SOF、截断头、解码失败和换档状态）。
