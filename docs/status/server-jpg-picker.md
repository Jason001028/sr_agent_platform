# 选择影像：路径组件与服务端 JPG 优先

日期：2026-11-10。代码已实现；内网实际 X 盘、UNC 和 4.56 GiB 原图仍待现场验收。

大文件组件修正：原生脚本的 Math.Max/Min 因首参数为 Int32 常量而选择错误重载，超过 2 GiB 的偏移/长度在采样阶段溢出，尚未进入服务端下采样。现偏移和长度比较明确使用 Int64，仅将不超过 4096 的采样缓冲长度转为 Int32。实际生产采样函数使用可寻址模拟流覆盖 1 字节到 8 GiB 七个大小，核对三处偏移、全部采样内容与最多 12288 字节读取；未因此宣称真实超大 TIFF 解码已验收。客户端必须覆盖安装更新后的组件，单独刷新网页不会更新已安装脚本。

## 当前流程

差异定位候选：下拉选择及「分析」调用 ensureCardPixels 自动取第二张图。候选已统一优先使用受限服务端缓存，包括未触发旧尺寸阈值的 ori/old；仅新接口明确返回 404 且尺寸安全时兼容旧取图路径。并发 A/B 各持有自己的控制，重复调用共享每张卡的在途 Promise；移除候选取消请求，迟到结果不写回。源 W/H、版本必须与候选一致，不新增生产权限，分析算法与掩码逻辑不变。

状态反馈显示准备缓存、排队、采样生成、下载、解码等阶段，等待期间提供已等待秒数。preview-status 仅查询内存队列状态与缓存元数据，不读取源像素或启动新生成。后台慢日志记录缓存命中/生产复用/新生成、总耗时和采样耗时，可区分真实盘阵冷读与排队。

口径纠正：ready-only 在当前后端返回 JSON 就绪信息，删除前置调用减少的是额外准备往返，不能据此宣称原来重复传输了整张 JPG。过去文档中的“丢弃 JPG 后再下载”判断不准确。

NOSR 档位联动：只对同景、实际尺寸更小的 NOSR 生效（两边不大于 PAN，至少一边严格更小；使用 W/H，不使用压缩后文件字节数）。PAN/通用档位为 1/4、1/8、1/16、1/32 时 NOSR 请求 1/2；PAN 为 1/2 或 1:1 时 NOSR 请求 1:1。缺少可靠同景 PAN 尺寸或等大/某边更大时，继续沿用全局选择。可从 siblings 的输入项尺寸或已加载同景 PAN 获得依据，不能借用其他场景。

全局滑块仍代表 PAN/通用基准；各卡片记录自己的请求档位。NOSR 已为 1:1 时，PAN 在 1/2 与 1:1 之间切换不会重复取 NOSR；离屏后再激活按各自有效档位检查缓存。NOSR 整幅 JPG 超过显示预算时，改用长边受限的服务端缓存概览，卡片同时标注请求档位与实际比例；“请求 1:1”不保证在安全概览里拿到全分辨率像素。后台预热也使用 NOSR 对应档位，并跳过超预算的隐藏整幅生成。

入口调整：左上角「选择影像」默认直接调用普通文件选择框，不显示组件弹窗，也不创建原生选择会话。组件安装包与「使用组件选择影像」入口放在「设置 → 影像路径组件（可选）」，由用户手动下载和调用。下面的原生路径流程仅在用户明确使用组件时运行；服务端 JPG 优先策略保持不变。

左上角「选择影像」提供 Windows 原生选择与普通文件选择两种入口。原生入口复用本项目的 sr-explorer 组件，取得用户选中文件的实际路径、大小和有界采样指纹。服务端先核对映射路径及内容；能直接读取就不上传原文件，立即请求服务端下采样 JPG。路径无法映射或服务端无法读取时，组件分块上传，再生成 JPG。普通 Chrome 文件选择无法提供真实绝对路径，因此先尝试已有盘阵核对，未命中则分块上传。拖入共用服务端 JPG 优先策略。

上述流程不要求先关联业务场景。上传缓存只授予预览能力，不凭文件名伪造 sceneId、盘阵目录或 SR 权限；匹配到真实源并通过核对后，才沿用 NOSR、ori、old 等同景入口。TIFF、JPEG、PNG 均可进入服务端预览；具体编码仍取决于服务端解码器支持。

预览 JPG 长边最多 4096，保留用户选择的档位并明确展示实际概览比例；这不是完整档位的区域细节读取实现。换档复用已上传原文件，已有兼容生产 JPG 可只读复用，不改写源目录。服务端失败时才回退原有本地读取。缓存过期后需重新选择文件。

## 暂停与停止

进度显示：服务端预览 HTTP 请求尚未提供逐行进度，因此等待期间使用不确定进度动画和「等待服务端处理」，不显示虚假的 0% 或模拟百分比。有真实回调的上传/本地读取阶段保留百分比，切换阶段重置旧值；暂停停止动画，减少动态效果偏好使用静态提示。这不区分服务端排队/采样/编码的实时占比。

连续大图的关联等待修正：已有服务端预览资产时，先取 JPG 并释放前台加载状态，再后台核对业务关联。核对成功且源版本/尺寸一致才开放关联能力；超时或失败不撤掉已显示 JPG，也不因此重传原图。关闭卡片/批量清除会取消其后台请求，迟到响应不得给其他卡片授权。默认选择器最初凭文件名寻找服务端源仍是必要步骤，不能在尚未找到源时凭空绕过。

现场诊断：`scene_resolve` 日志分开记录 `wait_ms`（解析通道排队）、`run_ms`（服务端执行）、`sample_ms`（三段采样核对）、`dims_ms`、`row_ms`。排队或执行超过 2 秒按 WARNING 输出；路径分支的尺寸/场景行构造合并在 row_ms。这些服务端日志不包含 Chrome 读取本地采样或网络往返时间。此次已修的是已知串行等待，不代表已测出用户第二张真实 4.8 GB 图的现场耗时原因。

本次连续加载修正验证：前端全量 89 文件 / 1008 项、类型检查及生产构建通过；后端关联与 image-open 组合 129 项通过。新增回归覆盖两张 JPG 在关联未返回时仍完成显示、延后授权、源版本变化拒绝授权、移除后取消与迟到结果隔离。

上传块为 4 MiB，暂停在块边界生效；停止撤销后续上传、下载及前端回填，不再自动启动本地解码。服务端已经开始的原生栅格计算不能强行终止，但保留任务所有权并在后台收尾，避免释放容量后重复并发。Windows 已打开的文件对话框需用户自行关闭，停止后其结果不会继续上传。

## 部署

同时更新后端并重启 API、发布完整 frontend/dist、更新 nginx 的 /api/image-open/ 代理配置。客户端重新下载 SrExplorer-Setup.zip，全部解压后运行安装器；旧版只支持打开目录，不能原生选择影像。

安装包新增 Pick-SrImage.ps1，共四个文件。安装器 PickerOrigins 默认只允许 http://10.10.81.135；实际网页/API 回调使用其他域名或端口时，安装时传入匹配的明确来源，不能放开任意回调地址。该配置与 Chrome 协议免提示策略独立。

服务端 W:、X: 默认都映射 /DiskArray；其他盘符通过 SR_DRIVE_MAP 配置。UNC 通过 SR_UNC_MAP 显式映射，例如 `\\host\share=/DiskArray;\\other\images=/mnt/archive`，并同时满足 SR_ALLOWED_ROOTS。未知 UNC 和本机磁盘路径走上传，不冒充服务器文件路径。Windows 用户本身仍需拥有读文件权限，网络盘需在该用户普通会话可访问。

## 缓存与容量

- SR_IMAGE_CACHE_ROOT：独立可写磁盘目录，建议 SSD；禁止文件系统根目录。不配置时，显式 SR_AGENT_DB 的父目录下使用 image-preview-cache；如配置 SR_TEMP_PREVIEWS_ROOT 则优先使用其 image-open 子目录，否则沿用临时预览根目录。
- SR_IMAGE_CACHE_TTL_SEC：默认 86400 秒，最少 300 秒；每 300 秒清理过期资产，包含上传原文件与 JPG。
- SR_IMAGE_UPLOAD_MAX_BYTES：默认 8 GiB，仅限制上传原文件；服务端直接可读源不受此上传限制。
- SR_IMAGE_CACHE_MAX_BYTES：默认 32 GiB，约束上传空间预留；JPG、元数据仍需额外磁盘余量，不是严格文件系统配额。

清理仅删除专用根目录中带本模块标记的资产目录，跳过上传或正在排队/执行的预览任务；不删除生产源图、生产 JPG 或其他缓存。缓存标识不暴露原始路径，选择票据使用随机能力令牌，调用方应避免把完整令牌写入公开日志。多用户计算沿用现有有界影像队列，缓存读取走独立通道。

对于服务端不可读的数 GiB 本地文件，首次上传耗时由网络决定，不能保证与盘阵直读一样快。默认同一批选择顺序装载，避免互相撤销上传。
