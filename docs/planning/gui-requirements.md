> **文档定位**：综合（方向 + 功能阶段里程碑 + 可落地需求，分层组织）。用于内部规划对齐、季度汇报支撑、GUI/agent 开发需求规格。

## 1. 背景与现状

### 1.1 已部署系统与工具

| 系统 / 工具 | 用途 | 状态 |
|------------|------|------|
| 生产结果管理平台 | 结合墨卡托投影世界地图管理生产结果 | 已上线 |
| 生产任务发起平台 | 发起生产任务 | 已上线 |
| 标签检查工具 | 检查某张图是否存在 / 打开对应文件夹 | 独立工具 |
| 卫星图像掩码生成工具 | 绘制、保存、可视化掩码；产出 `掩码.tif`（分辨率与原图一致）与 `掩膜中心点坐标.txt` | 独立工具 |

> 现有两平台（生产结果管理、生产任务发起）均由研发者（志兵哥）独立完成：技术栈为 Vue 2 + Spring Boot（前后端分离架构），界面工程自开源模板二次开发；部署方式为工程产物压缩包离线交付内网机，解压后由 Nginx 静态资源托管。标签检查、掩码生成属独立工具，非 Web 平台。

### 1.2 现状痛点

- **工具分散**：超分环节需在多个独立系统/工具间切换，无统一入口。
- **掩码→SR 链路手动衔接**：掩码由独立工具生成，需手工导入批量推理流程（`run_all_folders` 等）。
- **结果验证分散**：耗时/质量对比缺少统一可视化载体。

### 1.3 算法侧现状（已确认事实）

- SR 管线为 compute-bound（GPU 推理约占 91% 总耗时），显存非瓶颈。
- 部署目标为桌面端单卡（RTX 3060 级显存）；多卡（4×3090 服务器）判定为伪需求，不进入生产方向。
- 正式 TRT 部署由 GUI 平台统一完成；本管线本地仅确认大致加速效果。
- MTA-Grid 网格原点对齐已实现，收益集中在紧凑 + 小 ROI 场景。
- 掩码相关基础已就绪：`MaskPath` 缺省保护、批量推理脚本 `run_all_folders.py`（含后缀匹配、防删源文件保护）。

## 2. 目标态

### 2.1 总体目标

构建一个独立、统一的**超分环节管理与可视化平台**（Web），将分散的掩码绘制、参数配置、批量推理、模型/TRT 部署、结果对比收敛为单一入口；平台内分两层——**GUI 层（人机交互）**与 **Agent 层（自动化）**。Agent 先覆盖实验/验证闭环，再演进到生产端到端。

> **开发约束：本平台由单人独立开发**。因此范围控制优先：功能以最小可用为界，优先复用现成组件，小步增量交付，每个新增功能计入长期维护成本。

### 2.2 GUI 层能力（人机交互）

- **掩码绘制 + 参数配置**：交互式 ROI 绘制；tile / 模型 / scale 等参数配置；生成推理配置文件。掩码格式复用现有 `掩码.tif` + `掩码01点阵.txt`。
- **批量任务队列**：多文件夹任务（如 `/sr_data`）入队、进度监控、失败重试。
- **模型 / TRT 部署管理**：模型导入、TRT 导出与部署的统一入口。
- **结果可视化对比**：结果图对比、耗时表、质量指标展示。

### 2.3 Agent 层能力（自动化）

- **阶段一（验证闭环）**：掩码参数化生成 → MTA-Grid 规划验证 → 批量推理调度 → 耗时/质量对拍报告。
- **阶段二（生产端到端）**：数据进入 → 预处理 → SR → 输出 → 质量检查全自动。
- **函数调用（function calling）**：agent 通过函数调用驱动本地工具库（掩码生成、规划验证、批量推理、对拍报告、文件/目录操作等），是 agent 落地到实际业务场景的手段。

### 2.4 与现有系统关系

- **独立平台**：与现有两个 Web 平台并存，不并入。
- **接口打通**：以超分环节为主，与生产任务平台 / 生产结果管理平台打通数据流（任务下发、结果回传）。
- **掩码格式兼容**：直接复用现有掩码工具产物，不重做格式。

### 2.5 后续工作重心

- **本地工具库**：收集并实现 agent 可调用的本地工具集，优先复用现有实现（`run_all_folders`、MTA-Grid planner、掩码工具等），补足缺失项。
- **agent 函数调用能力**：增强 function calling 的编排、参数校验、错误处理与可观测性。
- **实际业务场景应用价值**：以上能力以在真实业务工作流中的可用性为准绳，而非仅作演示。

## 3. 功能阶段里程碑（按功能阶段）

| 阶段 | 交付物 | 主要覆盖 |
|------|--------|---------|
| M1 · 验证闭环 | Agent 跑通"掩码生成 → 规划验证 → 批量推理 → 对拍报告"；GUI 具备掩码绘制 + 参数配置 | Agent 阶段一 + GUI 基础 |
| M2 · 批量与可视化 | GUI 批量任务队列、进度监控、失败重试；结果可视化对比 | GUI 批量 + 可视化 |
| M3 · 生产端到端 | 模型/TRT 部署管理；Agent 生产端到端；与现有平台接口打通 | Agent 阶段二 + 接口集成 |

> 阶段间存在依赖：M2 依赖 M1 的批量推理基座；M3 依赖 M2 的任务管理与 M1 的 Agent 编排。
>
> **单人开发约束**：各阶段按最小可用交付，优先复用现成组件（§6.2）；每阶段完成即验证，避免一次性大而全。

## 5. 已确认决策 / 待定项

### 5.1 已确认决策

- 平台形态：新增独立 Web 平台，与现有两平台并存。
- 平台结构：GUI 与 Agent 同平台两层。
- Agent 演进：先验证闭环，后生产端到端。
- 覆盖边界：超分为主 + 与生产任务/地图平台接口打通。
- 掩码格式：复用现有 `掩码.tif` + `掩膜中心点坐标.txt`。
- 部署目标：桌面端单卡（RTX 3060 级）优先；多卡判定伪需求。
- TRT：正式部署由 GUI 平台统一完成。
- 开发模式：单人独立开发，范围控制 + 复用优先 + 增量交付。
- Agent 落地手段：通过函数调用（function calling）驱动本地工具库；价值以实际业务场景应用为准。
- 部署链路：对齐现有平台——工程产物压缩包离线交付内网机，解压后由 Nginx 静态资源托管（前后端分离，REST 接口对接）。
- 依赖获取：内网可安装第三方依赖（存在可用镜像/离线包），开源组件可直接采用。
- 参考工程：研发者（志兵哥）提供 Vue 2 界面工程（历史版本之一）作为 GUI 选型参考；现有两平台作为接口契约（I1/I2）与架构的参考实现。

### 5.2 待定项

- GUI 前端选型：参考工程为 Vue 2（研发者：志兵哥，见 §6.2）；倾向自研 React 栈（匹配现有技能栈 React + Nginx），待评估复用成本后定。
- 后端框架：待定（参考现有平台 Spring Boot；需评估与 Agent 侧 Python 生态的衔接）。
- Agent 实现架构（任务编排、调度方式、与 `run_all_folders` 的集成形态）。
- 与现有两平台的数据/接口细节。
- 功能阶段里程碑的时间绑定（M1/M2/M3 具体排期，结合单人全职/兼职节奏）。
- 性能与质量量化目标（如单图耗时上限、质量指标口径）。
- TRT 加速效果的量化验收标准。
